# 視覺管線深入設計說明（armor_vision — 綠色圓形靶標）

> 專案首頁：**[../README.md](../README.md)**；本文件是設計細節（雙投影原理、圓形先驗推導、
> 形態學空間偏移的數學、Vivado LUTRAM 推斷踩坑、逐項驗證對照）的深入說明。
>
> 飛鏢（dart）的靶標是**一個大綠色圓形燈**。本管線在官方 39 例程（OV5640 → DDR3 → RGB LCD）之上
> 插入一條純 Verilog 視覺管線，實現：
> **① 綠色分割（三個可調門檻）② 形態學閉運算 ③ 雙投影找綠塊 ④ 圓形先驗校驗 ⑤ 紅色圓環 + 中心十字 ⑥ 6 位數碼管顯示**
>
> 硬體：正點原子達芬奇 XC7A35TFGG484-2 ｜ OV5640 ｜ 4.3 吋 800×480 RGB LCD ｜ 板載 6 位共陽數碼管
> 驗證：`xsim` 自檢測試台 **33 項全部通過**

### 四個關鍵設計決定

**1. 為什麼用「雙投影」而不是 dart 的 `FindBond.v`（連通域標記 CCL）**

靶標只有**一個**大綠圓，這個特性讓「框住它」只需要兩個 1D 直方圖：

- 資源：兩個 `800×10bit + 480×10bit` 的 LUTRAM（實測 210 個 LUTRAM），
  沒有等價類合併、label 回收、256 標籤 BRAM、標籤 FIFO 這些容易出鬼的邏輯
- 除錯：兩個直方圖的數值可以直接看，門檻調不對一眼就看得出來
- 時序：X 與 Y 在**同一幀**內算完，框不慢幀

dart 的 `FindBond.v` 是完整 CCL（256 標籤 + 64bit BRAM 存每塊 `{top,bottom,left,right,num}` +
標籤 FIFO + 幀末掃全部標籤取面積最大），能同時處理多個目標。
本工程只需要單目標，所以用輕量替代；若之後要做多目標，直接照 `FindBond.v` 移植即可。

**2. 形態學窗口是「右下角對齊」，所以要補延遲**

`morph_nxn` 的窗口是 `window(x,y) = din(x-N+1..x, y-N+1..y)`，輸出的空間位置比輸入往右下偏移。
兩級串接（膨脹+腐蝕）共偏移 `N-1 = 8` 行/像素，所以：

- 二值圖在螢幕上會整體往右下偏 8 像素
- `video_delay` 把**原圖也延遲 8 行 + 8 像素** → 螢幕上原圖與二值圖完全對齊
- 圓環與瞄準點十字用同一套像素串流座標，所以環一定貼著看到的綠圓

> 這樣做的代價是 `video_delay` 需要 `8 行 × 800 × 16bit` 的 LUTRAM（實測 1664 個 LUTRAM）。
> 想省資源可以把 `MORPH_N` 改成 5（延遲變 4 行+4 像素）。

**3. 投影取「外沿」而不是「最長區間」**

舊版取「hist 連續 >= 門檻的最長區間」。問題是：LCD 面板有光澤，鏡面反射會在燈上打出一條
**橫貫的白色洞**（白色判不出綠）。洞上方的亮像素和下方的亮像素會被切成兩段，取到的那段
高度只有原來的一半 —— 框變小、圓心整體上移，看起來就是「識別不到了」。

改成「第一個 / 最後一個 >= TH_MIN 的位置」就只看外沿，中間的洞完全無影響。
代價是對「兩塊分開的綠塊」更敏感（會被串成一個大框），所以形狀校驗裡的
**寬高比 + 峰值高度** 必須留著。（實測數據見第 12 節。）

**4. 圓環用平方比較，不開根號**

`d2 = dx² + dy²`，環上 ⇔ `r_in² <= d2 <= r_out²`。兩個平方用組合乘法，Vivado 推斷成 4 個 DSP48
（`overlay_box` 一個模組就用掉全部 4 個：`r_in²`、`r_ou²`、`dx²`、`dy²`）。7A35T 有 90 個 DSP，綽綽有餘。

## 3. 雙投影為什麼能框住圓（數學推導）

設綠色圓在**二值圖座標**（即已經含形態學 +8 偏移）下是圓心 `(Cx, Cy)`、半徑 `R` 的實心圓。

**X 直方圖**：第 `c` 欄的亮點數

$$h_x(c) = \#\{y : (c-C_x)^2 + (y-C_y)^2 \le R^2\} = 2\sqrt{R^2 - d^2} + 1,\quad d = c - C_x$$

（離散弦長）。`h_x(c) >= \mathrm{TH\_MIN}` 的解集是一個**連續區間** `|d| <= d_{\max}`，
其中

$$d_{\max} = \sqrt{R^2 - \left(\tfrac{\mathrm{TH\_MIN}-1}{2}\right)^2}$$

所以「最寬的連續亮欄 run」= `[C_x - d_max, C_x + d_max]`，取寬度

$$W = 2\,d_{\max} + 1$$

同理 Y 方向 `H = 2 d_max + 1`。

**內縮量**：`R = 100`、`TH_MIN = 4` → `d_max = sqrt(100² - 1.5²) = 99.99` → `d_max = 99`（整數）。
於是

```
bl = 408 - 99 = 309 ,  br = 408 + 99 = 507 ,  W = 199
bt = 248 - 99 = 149 ,  bb = 248 + 99 = 347 ,  H = 199
```

也就是說，**框比圓的實際直徑各往內縮了 1 像素**（門檻把弦長 < 4 的邊緣欄排除了）。
這是「用直方圖門檻找邊界」這類方法的固有特性，不是 bug。

（外沿投影的實際條件比上式高强一點：取的是「第一個/最後一個 `h_x >= TH_MIN` 的欄」，
對單一凸塊而言結果一樣；但對於被眩光打洞的塊，外沿不受洞影響。）

**峰欄高度**：`max h_x = h_x(C_x) = 2R + 1 = 201`（圓的正中欄弦長 = 直徑）。
這個值可以拿來當「這個 run 到底是圓還是橫條」的判據（下節）。

## 4. 圓形先驗校驗（擋掉反光塊 / 雜色塊）

判定有效需要**同時**滿足四條：

| # | 判據 | 表達式（`proj_bond.v`） | 擋掉什麼 |
|---|---|---|---|
| 1 | 夠大 | `bw >= MIN_SIZE && bh >= MIN_SIZE` | 小碎點 |
| 2 | 不太扁 | `bw <= 2*bh && bh <= 2*bw` | **又寬又扁的反光橫條**、左右分開的兩塊 |
| 3 | 峰欄夠高 | `2*xp_best >= bh` | 上下 / 斜對分開的兩塊 |

判據 3 的物理意義：圓的正中欄弦長 = 直徑 = 高度，所以 `xp ≈ H`。
用外沿投影時 `bh` 是「整體外沿」，而 `xp` 是單欄的最高值；
若框其實是「兩塊分開的綠塊」被外沿串成，`xp` 會遠小於 `bh`。

> `tools/model_morph.py` 的第 4 組測試就是拿兩顆分開的圆去驗這三條：
> 左右分開（w=479 h=79）、上下分開（w=79 h=339）、斜對分開（w=279 h=239 peak=61）
> —— 三種都會被擋掉（`ok? False`）。

> 為什麼需要這些？因為 LCD 面板有光澤，環境光按**鏡面反射**射進鏡頭時會出現大塊眩光。
> 眩光本身是白的（`G-R ≈ 0`）通常過不了顏色判據，但它會**打洞**、也會把整幅畫面的曝光/白平衡拉走。
> 加上形狀先驗之後，即使顏色判據被拉偏，形狀不對的塊也不會被當成靶標輸出。

## 5. 形態學「右下角對齊」的精確推導

設輸入二值圖 `I` 是實心圓（圓心 `C`、半徑 `R`）。窗口約定 `win(x,y) = [x-N+1, x] × [y-N+1, y]`：

1. **膨脹**：`D(x,y) = 1` ⇔ 窗口內存在 `I=1`
2. **腐蝕**：`E(x,y) = 1` ⇔ 窗口內全部 `D=1`

`E(x,y)=1` ⇔ 對窗口內每個 `(u,v)`，都存在 `(p,q) ∈ [u-N+1,u]×[v-N+1,v]` 落在圓內。
對實心圓，這個「最近點」就是把 `C` 的各分量夾到該方框上取到的點。當 `C` 在方框的左上方時，
最近點就是方框的左上角 `(u-N+1, v-N+1)`；而它到 `C` 的距離隨 `(u,v)` 向右下單調增大，
所以最壞情況取在 `(u,v) = (x,y)`：

$$E(x,y) = 1 \iff \left|(x-N+1,\; y-N+1) - C\right| \le R$$

也就是說：**`E` 就是原圓整體往右下平移 `N-1`，半徑不變**。

這正是測試台期望值的來源：原圖圓心 `(400,240)`、`R=100`
→ 二值圖圓心 `(408,248)`、`R=100`（半徑沒縮水，只平移）。

> 這個結論對任何凸集都成立（推導只用到「最近點取在角落」），所以方形燈條的情況同樣是純平移
> ——舊版打靶紙的期望值 `208 = 200 + 8` 也是這麼來的。

## 6. 時間關係（重要）

| 事件 | 時機 |
|---|---|
| 像素累積到 `hist_x[]` / `hist_y[]` | 有效顯示行（消隱期不算；`y > Y_GUARD` 才算） |
| 掃 `hist_x` 找最寬欄 run | `rd_vsync` 脈衝後，**801 拍**（`WIDTH+1`，多一拍收尾最後一個 run） |
| 掃 `hist_y` 找最長列 run | 接著 **481 拍**（`HEIGHT+1`） |
| 合計 | 約 **1283 拍**；垂直消隱有 `1056 × 45 ≈ 47520` 拍，時間非常寬裕 |
| 邊界框出現 | **第 1 幀末**（X 與 Y 同幀算完，不像舊版要等 3 幀） |
| 0 FPS 時的重置 | 每幀末 `S_LATCH` 出結果後回 `S_IDLE`，`de` 一來就繼續累加下一幀 |

狀態機：`S_IDLE`（累加）→ `S_SCANX`（掃欄）→ `S_SCANY`（掃列）→ `S_LATCH`（出結果）→ `S_IDLE`。

**直方圖的清除**就搭在掃描那一趟：掃 `hist_x` 時順便把讀過的位址寫 0，掃 `hist_y` 同理。
這樣每個直方圖都只有**單一寫埠**（`we/addr/data` 用 mux 合成），Vivado 才願意推斷成 LUTRAM。

## 8. 按鍵 / LED / 數碼管

按鍵在板上是**低電平有效**（按下 = 0），LED **低電平點亮**，數碼管位選低電平選通、段碼低電平點亮。

綠色判據有**三個**門檻，所以 `key[0]` 改成「選哪一個」，`key[1]`/`key[2]` 對選中的那顆做加減：

| 按鍵 | 腳位 | 功能 |
|---|---|---|
| `key[0]` | T1 | 循環選擇要調的門檻：`TH_G` → `TH_G-R` → `TH_G-B` → `TH_G` |
| `key[1]` | U1 | 當前選中的門檻 +8（飽和到 255） |
| `key[2]` | W2 | 當前選中的門檻 −8（下限 0） |
| `key[3]` | T3 | 顯示模式切換（0 = 原圖變暗+標記；1 = 純二值圖） |

| LED | 腳位 | 意義 |
|---|---|---|
| `led[0]` | R2 | 目前在調 `TH_G` |
| `led[1]` | R3 | 目前在調 `TH_G-R` |
| `led[2]` | V2 | 目前在調 `TH_G-B` |
| `led[3]` | Y2 | 偵測到目標常亮；未偵測到時 1.5 Hz 閃爍（順便當心跳） |

**6 位數碼管**（`dig0` 是最右一位）：

| 位 | 顯示 |
|---|---|
| `dig5` | 門檻編號 `1`/`2`/`3`；**小數點亮 = 純二值圖顯示模式** |

## 9. 顏色判據（與 dart 的對照）

RGB565 先展成 8bit：

```
r8 = {R5, R5[4:2]}     g8 = {G6, G6[5:4]}     b8 = {B5, B5[4:2]}
```

| 判據 | 條件 |
|---|---|
| 綠 | `(g8 >= TH_G) && (g8-r8 >= TH_G-R) && (g8-b8 >= TH_G-B)` |

這個形式直接借自 dart 工程的 `dart_-fpga/fpga/ip/isp/Threshold_ip/src/Threshold.v`：

```verilog
g_mask <= (G >= THRESHOLD_G);
r_mask <= ((G - R) >= THRESHOLD_G_R);
b_mask <= ((G - B) >= THRESHOLD_G_B);
```

dart 那邊是 10bit 影像，測試台給的預設是 `400 / 130 / 130`（`video_stream_tb.sv`），
折算到本工程的 8bit 就是 `100 / 32 / 32`。
三個判斷式用的都是**帶符號差值**，所以「白」「灰」（`G-R ≈ 0`）不會被誤判成綠；
`G >= TH_G` 這一條同時兼任亮度閘，避免暗部雜訊。

> dart 的 `Threshold.v` 是 AXI-Stream 介面（`tdata/tvalid/tuser/tlast`），
> 本工程是 `lcd_driver` 那套 `de / x / y` 像素串流，所以只搬判據、重寫介面。

**闘 2：相對飽和度（本工程新加，尺度無關）**

```
mx = max(r8,g8,b8);  mn = min(r8,g8,b8);  chro = mx - mn;
100*chro >= mx * REL_SAT_PCT        // 預設 20（%）
```

闘 1 是**絕對**差值，整幅畫面變暗或變淡時判據會一起漂移。
相對飽和度只看「色度占最亮通道的比例」：整體變暗/變淡時分子分母同比例縮放，判據不變；
白光眩光 `chro ≈ 0` 會被干脆地排除。兩個閘是**串聯**的（都要過），
把 `REL_SAT_PCT` 設成 0 就回到純 dart 判據。

3. **瞄準點**：`aim_y = 248 - (199 × 64 >> 8) = 248 - 49 = 199`

> 這套數字有**獨立推演**：`tools/model_morph.py`（Python 參考模型）跑出完全一樣的結果，
> 而且不用跑 xsim 就能先試算「眩光帶多高會出事」。

## 12. 反光（眩光）問題：定位與處置

### 症狀

把 LCD 螢幕轉一點點角度，綠色圓就完全識別不到（或框只剩一半、圓心飄到上面去）。

### 三層原因

1. **相機層（主放大器）**：`rtl/i2c_ov5640_rgb565_cfg.v` 原本讓 OV5640 的
   **AEC（自動曝光）+ AGC + AWB（自動白平衡）全部開著**（表裡有 `0x3a13=0x43`、AEC 穩定區間
   `0x3a0f/0x3a10/0x3a1b/0x3a1e/0x3a11/0x3a1f`、AWB `0x5180~0x519e`，
   但**沒有**寫 `0x3503`（AEC/AGC 手動）也沒有 `0x3406`（AWB 手動））。
   眩光一進畫面就抬高整幅平均亮度 → AEC 縮短曝光 → **全畫面一起變暗**；
   反射光是白的 → AWB 推走白平衡 → 綠色判據的差值整體縮小。
   **局部眩光就這樣被負回授放大成整個目標消失。**
   > 本工程的處置**不靠關相機自動**（原因見下面「為什麼最後沒把相機鎖死」），
   > 而是把判據改成對這種整體漂移免疫的**尺度無關**形式。
2. **光學層**：LCD 的 γ、對比、色度隨視角變化很劇烈（離軸幾度飽和度就掉下來，直接穿過固定門檻）；
   眩光本身還有臨界角效應（鏡面反射光掃過鏡頭孔徑時是階躍式的，所以是「突然就沒了」）。
3. **演算法層**：門檻都是絕對值；更關鍵的是**取「最長連續 run」的投影會被眩光打出的洞切成兩半**。

### 對照 dart 的做法

dart 的相機是**固定曝光 + 固定增益**（`io/hikrobot/hikrobot.cpp`：
`ExposureAuto = OFF`、`GainAuto = OFF`、`ExposureTime`、`Gain`；`configs/standard4.yaml` 裡
`exposure_ms: 2`、`gain: 16`）。它的傳統分割也只用「灰度值 >= threshold」這一類**固定**門檻。

### 已實施的處置

| # | 措施 | 位置 | 成本 |
|---|---|---|---|
| 1 | 顏色判據加**相對飽和度閘**（尺度無關，**抗反光主力**） | `color_seg.v` | 約 72 LUT |
| 2 | 投影從「最長連續 run」改成**取外沿** | `proj_bond.v` | 約 20 LUT（反而更簡單） |
| 3 | （選配，**預設關閉**）相機固定曝光 / 增益：`CAM_LOCK_EN = 1'b1` 時寫 `0x3503=0x03` + 手動曝光 / 增益 | `i2c_ov5640_rgb565_cfg.v`（`tools/patch_camera_lock.py`） | 0 LUT |

#### 為什麼最後沒把相機鎖死（`CAM_LOCK_EN` 預設 `1'b0`）

dart 的相機是固定曝光，照搬很自然，但**固定曝光值必須按現場亮度標定**。
第一版直接把曝光寫死成 `0x0200` 並預設啟用，結果該值對現場太小 → 感測器輸出一整幀近乎全黑 →
而 `rtl/lcd_driver.v` 裡 `assign lcd_bl = 1'b1`（背光常亮），現象就是**背光亮著但螢幕全黑**，
非常像「屏壞了 / 沒連上」。同時那一版還寫了 AWB 手動增益 `0x3400/0x3401`，
但 OV5640 這組寄存器是 `[9:8]` 還是 `[11:8]` 沒有可靠依據（10bit 裝不下 `0x400`，
更像 `[11:8]`，即 1x 要寫 `0x04`），寫錯同樣導致畫面異常。

所以現在的做法是：

- **預設完全不動相機**（`CAM_LOCK_EN = 1'b0`，寫 `0x3503 = 0x00`，等同原廠自動曝光），
  抗反光由上面第 1、2 條**尺度無關**的算法措施承擔 —— 它們對相機自動曝光 / 白平衡的漂移天然免疫。
- 想要極致穩定性再開 `CAM_LOCK_EN = 1'b1`，並**上電看著 LCD** 標定 `EXP_15_8`
  （太暗加大、過曝減小，大致 `0x0100` ~ `0x2000`），換環境需重標。
- **完全不碰 AWB**（`0x3406` 保持自動），把無法驗證的寄存器格式風險直接移除。

### 效果（`tools/model_morph.py` 的獨立模型 + `tb_armor_vision.v` 的相位 2）

眩光帶橫貫圓心（py 225..255，高 31px，白色）：

| 眩光帶高 | 舊版「最長 run」 | 新版「取外沿」 |
|---|---|---|
| 0 | h=199, cy=248 ✓ | h=199, cy=248 ✓ |
| 10 px | **h=94, cy=195 ✗** | h=199, cy=248 ✓ |
| 20 px | **h=89, cy=193 ✗** | h=199, cy=248 ✓ |
| 30 px | **h=84, cy=190 ✗** | h=199, cy=248 ✓ |
| 40 px | **h=79, cy=188 ✗** | h=199, cy=248 ✓ |
| 60 px | **h=69, cy=183 ✗** | h=199, cy=248 ✓ |

**眩光帶只有 10px 就讓舊版的高度從 199 掉到 94、圓心 y 從 248 跳到 195** ——
那就是「轉一點點角度就識別不到」的現場。新版直到 60px 都還給出正確的 149/347。

> 實際的 bbox 寬度會隨眩光變寬而微微縮小（邊緣欄弦長本來就短，被吃掉幾個像素就掉到門檻以下）：
> 30px 時 310/506（w=197）、40px 時 311/505（w=195）。這是合理的，不是錯。

### 還沒做、但建議做的（物理層）

- LCD 貼**防眩光（霧面）膜**，或給鏡頭加一片與面板偏振方向正交的**偏振片**，
  可以把鏡面反射壓掉 90%+，這是真正的治本
- 若環境光經常變化：每次換場地重新按亮度調一次曝光（`EXP_15_8` / `GAIN_7_0`）

## 13. 瞄準點：打擊點在綠燈上方

### 需求

相機看到的是綠燈，但實際打擊點在燈的**上方一點**。兩者有一個固定的物理偏移
（設燈直徑 `Dt`、打擊點比燈心高 `Δh`，拿現有靶紙量一下就有）。

### 推導：不需要額外測距

針孔模型下，同一個 `f`、同一個距離 `D`：

$$
W = f_{px}\cdot\frac{D_t}{D}\;(\text{燈的表觀寬度})\qquad
\Delta_{pix} = f_{px}\cdot\frac{\Delta h}{D}\;(\text{打擊點的像素偏移})
$$

兩式相除，**距離 D 直接消掉**：

$$
\boxed{\Delta_{pix} = W\cdot\frac{\Delta h}{D_t}}
$$

所以只要知道「物理偏移 / 燈直徑」這個**無量綱比例**，就能直接從表觀寬度算出瞄準點的像素位置，
不需要單獨測距 —— 距離資訊已經被寬度隱含了。

RTL 裡就是一瓣：`aim_y = center_y - (寬度 * AIM_H_Q8) >> 8`，
`AIM_H_Q8` 是 Q0.8 定點，在 `blob_track.v` 裡是 **16 位輸入埠**（`aim_h_q8`），
所以 UART 寫 `0x05` 就能在線微調（見 §17）；預設值由 `armor_vision` 的 parameter 給。

> RM 靶標的實測值：燈直徑 **55mm**、打擊點在燈心上方 **80mm**
> → `AIM_H_Q8 = round(256 × 80/55) = 372`（= 1.449 倍燈直徑），**這就是現在的預設值**。
> 它大於 255，所以欄位必須是 16 位 —— 8 位版本會把它靜默截斷成 116（= 0.45 倍）。
>
> 模擬裡 `tb_armor_vision.v` 把主實例釘在 `16'd64`（讓瞄準點留在畫面內、好比大小），
> 另外建了一個 `u_blob_real`（`16'd372`）專門驗證「偏移超出畫面時飽和到 0」。

> ⚠️ **位寬坑**：Verilog 裡 `a * b` 的結果位寬 = `max(兩個運算元位寬)`，**不是兩者之和**。
> 寫 `wire [AW:0] up = (bw * AIM_H_Q8) >> 8;` 時乘法會被算在 11bit 上：
> `199*64 = 12736` 被截成 448，`>>8` 得 1 —— 瞄準點只抬了 1 像素（測試台當場抓到）。
> 必須先宣告夠寬的中間量：`wire [AW+7:0] up_full = bw * AIM_H_Q8;`。

### dart 工程怎麼做（對照）

dart 的相機看的也是燈心，另外疊一個**角度**偏移。它的距離是從「目標的表觀**面積**」反推的：

```c
// alg_proportional_navigation.c
target->photo_target_area = (w - 8.0f) * (h - 8.0f);   // 減掉影像處理加的 8px 寬
target->photo_target_distance = alg_lookup_table_query(&area_to_distance_lookup_table, area);
```

表定義在 `lib_table.h`（500 點，距離 50cm~1500cm，`area ∝ 1/D²`：50cm 時 2760，52.9cm 時 2457）。
拿到距離後它去做**彈道 / 下墜**補償（`task_control.c`）：

```c
target_atatact_theta = 30.0f;
target_atatact_theta -= (10.0f/400.0f) * photo_target_distance;   // 距離越遠角度越小
```

另外 `alg_proportional_navigation.h` 裡還有
`WORLD_VFOV_ADD_ANGLE_RAD_MAX/MIN = 10°/3°`（註解：「世界坐標系目標垂直視場角需要增加的角度
（考慮下降影響）」），也是按距離插值。

**結論：**

| 要補償什麼 | 需要知道距離嗎 |
|---|---|
| **目標本身的幾何偏移**（打擊點比燈高） | **不需要** —— 像素偏移 = `W·(Δh/Dt)`，取的是「寬度」這個距離代理量 |
| **彈道下墜**（飛過去會掉） | **需要** —— 它是**角度**偏移，與距離、彈速都有關；dart 就是靠面積查距離再查下墜曲線 |

本視覺管線只負責前者（也就是使用者問的那一項）。
下墜屬於飛控側，需要時直接把「表觀寬度」接過去即可 —— 數碼管上那兩位
（`目標寬度 ÷ 10`）就是這個量的實時顯示。

### 怎麼標定 `AIM_H_Q8`

1. 把靶子放在已知距離，讀數碼管上的「寬度/10」→ 得到 `W`
2. 量出「打擊點到燈心的物理距離 `Δh`」和「燈的實際直徑 `Dt`」
3. `AIM_H_Q8 = round(256 * Δh / Dt)`
4. 上電後看十字是不是正好落在想打的位置；不對就微調 `AIM_H_Q8`

> 例（RM 靶標）：燈直徑 55mm、打擊點在燈心上方 80mm → `256 × 80/55 = 372`。
> 此時畫面上燈寬 199px → 十字在燈心上方 `199×372/256 = 289` 像素處 ——
> 比環半徑（約 100px）大 3 倍，所以十字會落在**紅環外面很遠**。
>
> ### 取景必須對準打擊點，不是對準燈
>
> 偏移是 1.449 倍燈寬，比環半徑（0.5 倍燈寬）大得多。若把燈擺在畫面正中（`c_y ≈ 240`）
> 而燈寬 200px，瞄準點會被算到 $240 - 289 = -49$，**在畫面之外**。所以：
>
> $$1.449\,W \le c_y \le 479 - \tfrac{W}{2} \quad\Longrightarrow\quad W \le 245\text{ px}$$
>
> 推薦燈的表觀寬度做 100~130 px（燈心 y ≈ 390~420），瞄準點就落在畫面中心。
>
> ### 為什麼 `aim_y` 必須用飽和減法
>
> `aim_y <= cy_w - up_t` 是無符號減法：$c_y < \text{up}$ 時會**下溢回繞**到 1024 附近，
> 十字跳到畫面底部（看起來像演算法壞了）。以前 `AIM_H_Q8 = 64`（偏移 0.25 倍寬）幾乎碰不到，
> 換成 372 之後**必然**碰到，所以 `blob_track.v` 改成先補到 19bit 比較再減、小於則輸出 0。
> 驗證在 `tb_armor_vision.v` 的 `u_blob_real`：372 下 `aim_y` 必須是 **0**，不是 1023 附近。

## 14. 已知限制與後續方向

- **只輸出一個目標**：取 X/Y 直方圖的外沿，畫面同時出現多個綠塊時會被串成一個框
  （**會被形狀校驗擋住 → 不輸出**）
  → 需要多目標就要移植 dart 的 `FindBond.v`（256 標籤 CCL + BRAM 存每塊結構 + 幀末取面積最大）
- **沒有彈道下墜補償**：只給圓心與瞄準點（目標幾何偏移）。下墜是**角度**偏移，和距離、彈速都有關，
  屬於飛控側；dart 用的是「表觀面積 → 距離 → 下墜曲線」兩步算，本工程已經把「表觀寬度」
  放在數碼管上，需要時可以直接接過去
- **相機固定曝光是「選配」且預設關閉**：`CAM_LOCK_EN = 1'b0` 時相機保持原廠自動曝光 / 自動白平衡，
  抗反光完全由兩條尺度無關的算法措施承擔。想要 dart 那種「曝光鎖死」的極致穩定性，
  把 `CAM_LOCK_EN` 打開並按現場亮度標定一次（換環境要重標 —— 這是拿通用性換穩定性）
- 其他可延伸：瞄準點經 UART 送給雲台 / 加 ILA 觀察兩個直方圖峰值
- 對應《RM飛鏢FPGA視覺方案》文件的階段 1~6 皆已完成（驗證對照見第 11 節）

## 16. PL 增強路線圖（對標 dart2026）

讀過 dart 的 PL 側（`dart_-fpga`）後的結論：**dart 的 PL 強在「特徵提取完整度 + 平台化」，
弱在「自適應與時序」** —— 後者恰好是純 RTL、沒有 PS 的我們最該補的地方。

對比要點：

| 能力 | dart PL | 本專案 |
|---|---|---|
| 二值化 | `Threshold.v`：`G≥T_G && G-R≥T_GR && G-B≥T_GB`（三閾值皆 AXI 寄存器） | `color_seg.v`：**同樣三條 + 相對飽和度閘**（多一道，尺度無關） |
| 形態學 | `ExpansionAnd → Expansion → Corrosion` 多級 | 9×9 膨脹 → 9×9 腐蝕（閉運算） |
| 特徵提取 | **`FindBond.v` 真 CCL**：256 標籤、每標籤 64bit 結構存 BRAM、並查集重標、累加面積 | **雙投影取外沿**：單框、無面積、多目標必掛 |
| 多目標 | `bond_dma.v`：每幀**全部** blob 打包 128bit 寫 BRAM + 計數 → PS | 無 |
| 參數下發 | AXI-Lite 寄存器 + Linux 驅動，執行時可改 | 按鍵 + 數碼管，手動 |
| 結果上報 | IRQ + AXI 回讀 + DMA 列表 → PS → 飛控 | 只有 LCD / 數碼管 / LED（給人看） |
| 除錯 | VDMA → DDR + JPEG 編碼 + WiFi 推流 + `system_ila` | 只有 LCD |
| **時序濾波 / 跟蹤** | **無** | **無** → 兩邊都沒，是本專案的差異化空間 |

### P9：為什麼遠處的燈「螢幕上有高亮卻認不到」

現場症狀：把綠色圓燈拉遠，LCD 上仍能看到高亮（那是 `color_seg` 的掩碼本身，顯示走 `mask_d`），
但 `bond_valid = 0`、沒有紅圈、沒有瞄準點。

根因在 `blob_track.v` 的選塊迴圈：

```verilog
if(r_used[mi] && (r_area[mi] >= MIN_AREA))   // MIN_AREA = 400，而遠燈只有幾十像素
```

**面積不夠的塊連「候選」都不是，最大的那塊也被丟掉**，於是整幀 `best_any = 0`。
和反光無關、和閾值無關 —— 就是一條寫死的面積門檻。

修法：兩級門檻。嚴檔（>= `MIN_AREA`）優先，沒有嚴檔時接受「面積 >= `min_area_lo` 且形狀合理」的塊：

```verilog
ss_ok = (tw <= (th << ASPECT_SHIFT)) && (th <= (tw << ASPECT_SHIFT))   // 長寬比 <= 8:1
     && ((r_area[mi] << 2) >= tp_c);                                   // 填充率 >= 1/4
```

形狀合理性**只作用於寬鬆檔**：面積小的時候填充率 / 長寬比對噪聲極敏感（一個 3x3 的燈
fill 就是 256），所以不能用圓的 π/4 去卡小目標，只擋「細長條」和「空心塊」。

- `min_area_lo` 預設 **8**（非常靈敏：只要有一小撮綠像素就報出來），UART `0x04` 可執行時調大
- `min_area_lo = 0` → **關閉寬鬆檔，行為與舊版逐位元一致**（逃生開關）
- `blob_far` / 上報 flags.b6 會告訴上層「這一幀是小而遠的目標」

副作用與取捨：門檻放低後，畫面裡的綠色噪點也可能成為候選。緩解手段有四層：
相對飽和度閘（尺度無關）、形狀合理性、取面積最大的那塊、以及 `TRK_EN`（門控 + 持久性）。

### P10：預測打中位置（lead）

舵機跟蹤要的是「燈**現在**在哪」；要打中要的是「飛鏢**飛到時**燈在哪」。
兩者差一個 `飛行時間 × 目標速度`，距離越遠 / 目標越快差得越多。

```
v_q4 <= v_q4 + (( (cx - cx_prev)<<4 - v_q4 ) >>> 2)      // α-β 速度估計，Q4
pred  = clamp( cx + ((v_q4 * LEAD_Q4) >>> 8) )           // 外推，飽和到畫面內
pay   = pred_y - up,   up = bw * AIM_H_Q8 / 256           // 幾何偏移，和 blob_track 同一公式
```

- 兩者都走 `raw_*`（不經 `TRK_EN` 門控），**不加延遲**：舵機跟蹤要的就是快
- 歷史不足（連續有效 < 2 幀）/ 關閉 / 本幀無效時 `pred_ok = 0`，輸出**直接鏡像當前幀**
  → 靜止目標下開 / 關預測的輸出逐位元一致，不會動到已驗收的行為
- `LEAD_Q4` 預設 64（= 4.0 幀，30fps 下約 133ms），UART `0x0A` 可調；
  知道彈速和距離就把它換算成幀數填進來（`LEAD_Q4 = 16 × 飛行時間 / 幀週期`）
- LCD 上：紅色十字 = 當前幾何瞄準點，**黃色十字 = 預測瞄準點**（只在 `moving` 時畫）

> 為什麼不直接用 `TRK_EN` 的 α-β 速度：那條路徑有 `HIT_N` 幀的確認延遲（門控 + 持久性），
> 對舵機來說太慢。預測模組自己做一套輕量速度估計，兩者互不干擾。

### 兩處刻意偏離原方案（重要）

**P3：用「行程級團塊跟蹤」而不是 dart 的「256 標籤逐像素 CCL + 並查集」**
dart 的 `FindBond.v` 需要一條 800 深的標籤行緩衝 + 256 項 64bit 結構體表 + 重標表，
還要一套 3 級流水在同一拍裡解決左右/上下標籤衝突。本專案的 `blob_track.v` 改成：
每行抽出 mask 的**連通行程**，與 4 個團塊記錄做「水平區間重疊 + 行相鄰」匹配，
命中多個就合併（面積/矩相加），都沒命中就新建記錄。
輸出（每塊外框 + 面積 + 形心 + 圓度 + 數量）與 dart 那套**完全一致**，但不需要逐像素
標籤 RAM 和並查集表，邏輯量約為前者的 1/4，也更好在測試台裡逐項驗證。
代價：最多同時跟蹤 `K=4` 個團塊（對「一個大的燈」這種靶標綽綽有餘）。

另外這裡**不需要 FIFO 和狀態機**：`emit` 只在 mask 由 1 變 0（或行尾收尾）時產生，
兩次 emit 至少隔 2 拍，而匹配判定 + 記錄更新是純組合的，正好在 emit 那一拍吃完 ——
一拍一個行程、零丟棄、無吞吐瓶頸。

**P8：OSD 第四行放填充率而不是距離**
面積反推距離要開根號，而且相機/鏡頭沒標定之前絕對值沒有意義。
所以 F3 顯示 `fill_q8`（圓的理論值約 201，一眼看出圓不圓）。
要距離請拿 F2 的面積在上位機裡算，那裡做 sqrt 是免費的。

### 邊界定義的變化（導致舊測試台的期望值要放寬 1~2 像素）

舊的 `proj_bond` 取直方圖外沿時有 `TH_MIN=4` 的裁剪：邊界上只有 1~3 個亮像素的
行/列會被丟掉。新的 `blob_track` 報的是**全部亮像素的真實外延**，所以外框會寬 1~2 像素
（圓心不變，仍是 408/248）。這不是錯誤而是定義變準了，因此測試台對邊界改用
`chk_near(±2~3)`，而圓心 / 瞄準點 x / 有效性仍然精確比較。

## 17. 對外介面：UART 上報與參數寫入

### 結果上報（P1，`result_frame.v`）

每 `TX_DIV`（預設 8）幀發一條定長幀，115200 8N1。**v2 = 24 位元組**（位元組 0~14 的含義與 v1 完全一致）：

| 位元組 | 內容 |
|---|---|
| 0 / 1 | `0xA5` / `0x5A` 幀頭 |
| 2 | flags：b0=`valid`、b1=`adapt_ok`、b2=二值顯示、b3=保留、b4=`pred_ok`、b5=`moving`、b6=`far_small`、**b7=1（v2 標記）** |
| 3 / 4 | 圓心 x（16bit，高/低） |
| 5 / 6 | 圓心 y |
| 7 / 8 | 瞄準點 x（**當前幀**的幾何瞄準點，語意同 v1） |
| 9 / 10 | 瞄準點 y |
| 11 | 外框寬（飽和到 255） |
| 12 | 面積 >> 7（飽和到 255） |
| 13 | `fill_q8` 填充率（圓約 201） |
| 14 | 本幀合格團塊數 |
| 15 / 16 | `vx_q4` 速度估計 x（Q4 有符號，**16 = 1 px/幀**） |
| 17 / 18 | `vy_q4` 速度估計 y |
| 19 / 20 | 預測燈心 x（LEAD 幀之後） |
| 21 / 22 | 預測燈心 y |
| 23 | checksum = byte2..byte22 逐位元組異或 |

> **雲台 / 飛控要打提前量，就指向** `(px, py - w × AIM_H_Q8 / 256)`（`AIM_H_Q8 = 372` 是常數）。
> 只想知道「現在瞄哪裡」就繼續用 `ax/ay`，語意沒變。
>
> **為什麼校驗和從 byte15 搬到 byte23**：v2 的 flags.b7 置 1，舊解析器用 v1 的
> 「byte2..byte14 異或 == byte15」必然驗不過 → 舊程式會**安全地丟棄**新幀，
> 而不是把 `vx_q4` 當成校驗和讀出垃圾資料。`tools/uart_parse.py` 已同時支援兩種長度，
> 並且會把 Q4 速度換算成 px/幀 顯示。

    > **已接好引腳**：`uart_rxd` = **U5**（input）、`uart_txd` = **T6**（output），
    > 電平 LVCMOS33，取自《達芬奇開發板IO引腳分配表》，已在 `pin.xdc` 裡約束。
    > （表上另有 `uart2_txd`=R19 / `uart2_rxd`=P19，那是 ATK 模組介面，未使用。）
    >
    > PC 端解析：`python tools/uart_parse.py COM3`（需 pyserial）；
    > 離線解析：`python tools/uart_parse.py --hex "A5 5A ..."`；
    > 下發參數：`python tools/uart_parse.py COM3 --set 0x07 0x01`。

### 參數寫入（P2，`reg_file.v`）

每條命令 **4 位元組**：`0xAA  addr  data  (addr ^ data)`，校驗不過整條丟棄。

| addr | 參數 | 預設 |
|---|---|---|
| `0x00` | `TH_G` | 100 |
| `0x01` / `0x02` | `TH_G-R` / `TH_G-B` | 32 |
| `0x03` | `REL_SAT_PCT` 相對飽和度閘限（>100 夾到 100；**0 = 關閉該閘**） | 20 |
| `0x04` | **寬鬆檔最小面積** `min_area_lo`（0 = 關閉寬鬆檔，回到「只認 >= 400 像素」） | 8 |
| `0x05` | `AIM_H_Q8` 低 8 位（小數部分） | 116 |
| `0x06` | `RING_T` | 2 |
| `0x07` | `CTRL`：b0=自適應 b1=中值 b2=曝光閉環 b3=二值顯示 b4=OSD **b5=速度預測** | 0（全關） |
| `0x08` | `GATE` 門控半徑 | 96 |
| `0x09` | `ADAPT_PCT` 自適應前景佔比 | 15 |
| `0x0A` | `LEAD_Q4` 預測提前量（幀 × 16，Q4；64 = 4.0 幀 ≈ 133ms @30fps） | 64 |

> **`0x03` / `0x04` 以前是死寄存器**：`reg_file` 一直有這兩個位址，但 `armor_vision.v`
> 裡只有宣告、沒有接進 `color_seg` / `blob_track`（和當時 `0x05` 的坑一樣：文件寫了、程式沒接）。
> 這次一起接上了：`0x03` 現在真的改相對飽和度閘限，`0x04` 改成寬鬆檔最小面積。
> `0x08`（`GATE`）/ `0x09`（`ADAPT_PCT`）/ `0x06`（`RING_T`）仍然是 parameter-only，
> 寫了不會生效 —— 要用的話按同一套路徑接即可。
> `MIN_SIZE` 這個 parameter 目前已無消費者（形狀校驗改由 `blob_track` 內部的
> 長寬比 + 填充率負責），保留只是為了不破壞既有例化。

> **`0x05` 的位寬說明**：`AIM_H_Q8` 是 16 位（RM 靶標要 372），而 UART 寄存器一次只傳 1 位元組，
> 所以協定定為：**`0x05` 只覆蓋低 8 位（小數部分），高 8 位沿用 parameter**。
> 372 = `16'h0174` → 高 8 位 1、低 8 位 116，而 `reg_file.v` 的 `r_aim_h` 復位值也正是 116，
> 所以「只寫別的閾值寄存器」不會動到瞄準高度；寫 `0x05` 可在 1.0~1.996 倍之間微調
> （步長 1/256 = 0.0039 倍燈直徑）。要在線設到 > 1.996 倍就改 `armor_vision.v` 的 parameter 重新綜合。
>
> 早期版本這裡有個**文件與程式不符**的坑：文件寫了 `0x05` = `AIM_H_Q8`，
> 但 `rf_aim_h` 在 `armor_vision.v` 裡只宣告、沒接進 `blob_track`（等於寫了沒用）。
> 現在已接上，而且是**輸入埠**（`aim_h_q8`）而不是 parameter —— parameter 只能用常數覆蓋，
> 接不了運行時寄存器（xvlog 會報 `'aim_h_eff' is not a constant`）。

寫過一次參數之後，閾值就以寄存器為準；沒寫過則完全沿用按鍵行為 ——
所以**預設行為與加 UART 之前一模一樣**，這也讓它適合當回退手段。

### P0 細節（`vision_stat.v`）

純觀測模組，不參與任何判決、不改畫面。`vsync` 一律走**邊沿**判定：
`tb_armor_vision` 裡 `vsync` 是「寬 101 拍的電平」而非單拍脈衝，真機 `rd_vsync` 形態也不好假設；
若直接拿電平當條件，寬 `vsync` 會把計數器反覆清零，`frame_cyc` 恆為 0。

- **上升沿** = 幀起點 → 鎖存上一幀統計量並清零
- **下降沿再晚一拍** = `frame_tick`，此時 `proj_bond` 本幀結果已穩定（命中率就在這裡採樣）

`fps` 用「1 秒窗口數 `vsync` 個數」實現，省一個除法器，而且給的是**真實平均值**
（幀週期抖動時比瞬時值更有參考價值）。但仿真裡不可能真跑 1 秒，
所以測試台**另建一個 `CLK_FREQ = 2×(H_TOTAL×V_TOTAL)` 的實例**，窗口正好等於 2 個幀週期
→ `fps` 應恆為 2，可精確斷言（比斷言 1 強，能排除「計數器卡住」的巧合）。

資源：幾個飽和計數器，約 120 LUT / 100 FF，**0 BRAM**。
P0 階段這些統計量還沒有下游消費者（UART 在 P1 才接），所以例化上加了
`dont_touch` 把實例釘住，否則綜合器會整塊優化掉、`mark_debug` 抓不到東西；P1 之後可以拿掉。

從紅藍版升級到綠色版：`python tools/patch_green.py`（可重複執行，已套用過）。

## 20. 彈道補償（P11）：由表觀寬度反推距離與下墜

### 需求

飛鏢飛行過程中會下墜（5m、彈速 20m/s 時 t=0.25s，自由落體已經 30cm），
所以「瞄準點」不等於「燈心 + 幾何偏移」，還要再抬一個下墜量。
PL 沒有測距儀，唯一可用的距離線索是**表觀寬度 w**。

### 推導：兩件事都只是 1/w

相機焦距（像素）`f_px = 2570`（第 13 節推過）、靶標燈直徑 `D = 55mm`：

```
dist_mm = f_px * D / w = 141350 / w        ->  dist_cm = 14135 / w
```

下墜是世界座標的量，但要補在【像素】上：

```
dist_m    = dist_cm / 100
t         = dist_m / v0                 (v0 = 彈速)
drop_m    = g*t^2/2
px_per_mm = w / D                     <- 這一項也含 w
drop_px   = drop_m * 1000 * px_per_mm
```

把 `dist_m ∝ 1/w` 代進去，w 只剩一次冪：

```
drop_px = 4454.5 / w                  (v0 = 20 m/s)
```

**所以兩張 256 項的表都只是 1/w** —— 零除法、零乘法、時序零風險。

換彈速也不用重新綜合：寫 UART `0x0B` 的 `DROP_SCALE`（Q8，255 = 20m/s）：

```
DROP_SCALE = round(256*(20/v0)^2) - 1
20m/s -> 255     25m/s -> 163     30m/s -> 113     15m/s -> 454
```

### 實現

`rtl/ballistic.v`（兩張表由 `tools/gen_ballistic_lut.py` 生成，改公式就重跑那個腳本）：

```
dist_cm = ROM_DIST[bw]                                (bw > 255 飽和；bw < 8 視為無效)
drop_px = (ROM_DROP[bw] * (DROP_SCALE+1)) >> 8
fx      = 預測燈心 x
fy      = 預測燈心 y - (w*AIM_H_Q8/256) - drop_px     (單調飽和，減不夠就取 0)
```

`dist_ok` = 有目標且寬度在表內（`bw >= 8`），上報在 flags.b3。

### 與速度預測的關係

`aim_predict`（提前量）與 `ballistic`（下墜）是兩個獨立的修正，串在一起：

```
預測燈心 -> 幾何偏移（打擊點在燈上方）-> 下墜補償 -> fx / fy
```

**雲台直接用 `fx/fy`**，不用自己重算。中間量（cx/cy、px/py、dist_cm、drop_px）也全都上報，便於調試。

### 校準

1. `f_px` / `D` 寫在 `tools/gen_ballistic_lut.py` 頭部 —— 改完重跑腳本 + 重新綜合；
2. 彈速用 UART `0x0B` 在線調（**不用重新綜合**），打幾發看落點偏移再微調；
3. 想知道 `f_px` 到底是多少：把燈放在已知距離，讀數碼管/OSD 上的寬度，
   `f_px = w * dist_mm / 55`。

## 19. 時序：50MHz 下的 setup 違例與三級流水

### 現象

P9（兩級面積門檻）之後跑 implementation：

```
[Timing 38-282] The design failed to meet the timing requirements.
   WNS -5.242 ns   TNS -48.373 ns   Failing Endpoints 10 / 46587
```

### 定位（兩個小工具）

```
python tools/timing_peek.py          # 讀 impl_1 的 timing_summary_routed.rpt，抽重點
vivado -mode batch -source tools/timing_peek.tcl -nojournal
                                     # 直接在 routed checkpoint 上列【所有 slack < 1ns】的路徑
```

`timing_peek.tcl` 是關鍵：summary 報告只有「最差的 10 條」，修完一條後下一條如果只是
`-0.1ns` 就要再等十幾分鐘重跑實現。一次把所有逼近極限的路徑列出來，才能一輪修完。

結果非常乾淨：

| 路徑 | slack |
|---|---|
| `u_blob_track/r_l_reg[0][6]/C` → `u_blob_track/aim_y_reg[9:0]/D`（10 位 = 10 個端點） | **-5.242 ns** |
| 其餘全部（含 MIG / DDR3 / LCD / 相機路徑） | ≥ **+0.98 ns** |

時鐘是 `clk_out2_clk_wiz_0`（**50 MHz，20 ns**），不是像素時鐘的 25 MHz —— 這條管線的
時序預算只有 20 ns，不是 40 ns。

### 根因

P9 把形狀合理性檢查（4 個候選各一個 `w*h` 乘法 + 長寬比/填充率比較 + 兩級優先樹）
塞進了原本「選塊 → 幾何換算（`bw × AIM_H_Q8` → 飽和減法 → `aim_y`）」的**同一條**組合鏈：

```
r_l_reg[0] ─┐
            ├─ 4×(w*h 乘法 + 比較 + 優先樹) → best_i → mux → bw_w → ×372/256 → 飽和減法 → aim_y_reg
r_area      ─┘                              25.160ns（logic 14.313 + route 10.847）
```

模擬看不出來（`synth_check_vision.tcl` 是 **out-of-context 綜合，沒有任何時序約束**），
只有 implementation 才報。

### 修法：三級流水（`tools/patch_blob_timing.py`）

```
級 0（組合）  形狀合理性：4 個候選並行 w*h + 比較            → shp_now
級 1（寄存器）shp_ok_r      <- shp_now      ← 乘法移出選塊路徑
級 2（寄存器）best_i_r / best_any_r / best_far_r / cnt_r   <- 選塊結果
級 3（寄存器）sl_r/sr_r/st_r/sb_r + sa_r/sx_r/sy_r + sany_r/sfar_r/scnt_r
級 3 之後（組合）cx_w / cy_w / bw_w / up_t / ay_s → 在 vsync 下降沿採樣
```

**為什麼加幾拍完全不會改變行為**（這是不動邏輯就能修時序的關鍵）：

- 團塊記錄只在一幀裡 `emit` 時才改變，而結果只在 **vsync 下降沿**取用 —— 中間隔著幾百拍；
- 記錄清空同樣發生在 vsync 下降沿那一拍，而輸出端讀的是**清空之前**就已經打進流水線的值
  （nonblocking 語義下，同一拍的 `<=` 讀到的是該拍之前的狀態）；
- 所以只要「最後一次 emit → vsync 下降沿」≥ 流水級數（3 拍），時序上是等價的。

實測：**90 項自檢逐項不變**（`ALL CHECKS PASSED`），包含遠/小目標、速度預測、UART v2。

### 教訓

- 這種「一幀內準靜態」的資料（團塊記錄、選塊結果、幾何參數）**可以隨便打拍**，
  代價只是一次性的幾十個 FF —— 這是純 RTL 設計裡最便宜的時序修法；
- 相對地，**逐像素**的資料流（行緩衝、形態學、投影）不能亂加拍，那要算好對齊；
- 新增邏輯後要盯住「這一條組合鏈有多長」，`w*h` 這種乘法尤其危險；
- OOC 綜合綠燈 ≠ 時序收斂，兩件事都要跑。


## 18. 兩個「仿真過、實現掛」的坑（多驅動網路）

xsim **容忍**同一個 reg 被多個 always 塊驅動（它自己挑一個，跑起來「看起來正常」），
Vivado 則直接拒絕：

```
[Synth 8-6859] multi-driven net on pin u_armor_vision/u_chroma_hist/hgb[255][19] ...
[DRC MDRV-1] Multiple Driver Nets: Net .../Q[0] has multiple drivers (99 more like this)
[Vivado_Tcl 4-78] Error(s) found during DRC. Opt_design not run.
```

> 結論：**仿真全過 ≠ 能實現**。新增任何 always 塊之後，都要回頭確認自己寫的 reg 沒有第二個驅動源。

### 兩處病灶

| 檔案 | reg | 症狀 | 修法 |
|------|-----|------|------|
| `chroma_hist.v` | `hgr` / `hgb` / `total` | 直方圖「掃描時清零」與「工作時累加」各寫一次；`total` 也是兩塊都寫 | 寫口合成**單一寫埠**：`hist_we = scanning \| (de & ~scanning)`，`h_addr`/`h_addr_b` 用 mux 在掃描地址與像素地址間選，下一個值 `hgr_nx`/`hgb_nx` 也 mux 好，只留**一個**時序塊寫陣列；`total` 只由掃描 FSM 驅動 |
| `osd_text.v` | `conv_done` | 轉換 FSM 裡置 1/清 0，數字刷新塊裡用完又清 0 | 只留 FSM 驅動，並改成單拍脈衝 `conv_done <= (cv_state == CV_SAVE) && (cv_sel == 2'd3);`；刷新塊**只讀不寫** |

`osd_text.v` 的**復位分支**裡也有一行 `conv_done <= 1'b0;` —— 那是**同一塊內**的賦值，合法；
刪的時候要連帶後一行 `nd0 <= ndig(b0_bcd);` 一起當錨點，否則會誤刪。

腳本：`python tools/patch_fix_multidriver.py`（純 ASCII 錨點 + 回讀比對，可重複執行）。

### 自查方法

1. 每個時序塊寫的 reg，全域搜尋它一共出現幾次 `<=` 賦值；跨到 >1 個塊就是多驅動。
2. 記憶體（陣列）最容易踩：「清零」與「累加」寫在**同一個** always 的兩個 `if` 裡是合法的，
   寫在**兩個** always 裡就是多驅動。而且多寫埠還有第二個副作用 —— **擋掉 RAM 推断**（見 §7）。
3. 最終驗收只能靠綜合：`vivado -mode batch -source tools/synth_check_vision.tcl -nojournal`，看 `ERROR` 數量為 0。

### 順帶：`pin.xdc:49` 的警告

```
[Common 17-55] 'set_property' expects at least one object. [pin.xdc:49]
```

`set_property CLOCK_DEDICATED_ROUTE FALSE [get_nets cam_pclk_IBUF]` 抓的是**自動推導出來的網名**，
換版本/換綜合設定就可能抓不到。這是**專案既有**的警告，與本次改動無關，不影響實現。
