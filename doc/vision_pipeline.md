# 视觉管线深入设计说明（armor_vision — 绿色圆形靶标）

> 专案首页：**[../README.md](../README.md)**；本文件是设计细节（双投影原理、圆形先验推导、
> 形态学空间偏移的数学、Vivado LUTRAM 推断踩坑、逐项验证对照）的深入说明。
>
> 飞镖（dart）的靶标是**一个大绿色圆形灯**。本管线在官方 39 例程（OV5640 → DDR3 → RGB LCD）之上
> 插入一条纯 Verilog 视觉管线，实现：
> **① 绿色分割（三个可调门坎）② 形态学闭运算 ③ 双投影找绿块 ④ 圆形先验校验 ⑤ 红色圆环 + 中心十字 ⑥ 6 位数码管显示**
>
> 硬件：正点原子达芬奇 XC7A35TFGG484-2 ｜ OV5640 ｜ 4.3 吋 800×480 RGB LCD ｜ 板载 6 位共阳数码管
> 验证：`xsim` 自检测试台 **33 项全部通过**

## 2. 管线架构

```
DDR3 读出 (rddata / rdata_req / rd_vsync)
        │  RGB565 800×480 @ lcd_clk
        ▼
  输入打一拍对齐 (data_v / x_v / de_v)
        │
        ▼
  ┌──────────────┐  两道闸：
  │  color_seg   │  ① 绝对（借自 dart 的 Threshold.v）
  │              │     mask = (G>=TH_G) && (G-R>=TH_G-R) && (G-B>=TH_G-B)
  └──────────────┘  ② 相对饱和度（尺度无关，抗反光）
        │             100*(max-min) >= max*REL_SAT_PCT
        │  seg_mask (1bit)
        ▼
  ┌──────────────┐  ┌──────────────┐
  │ morph_nxn    │→ │ morph_nxn    │   膨胀 9×9 → 腐蚀 9×9 = 闭运算
  │ DILATE=1     │  │ DILATE=0     │   (填绿圆内部小洞、去碎点)
  └──────────────┘  └──────────────┘
        │  ero_mask（顶端 2*(N-1)=16 行视为 0，行缓冲尚未填满）
        │  mask_d = ero_mask & (y_cnt > Y_GUARD)
        ├───────────────────────────┬──────────────────┐
        ▼                           ▼                  ▼
  ┌──────────────┐          ┌──────────────┐   ┌──────────────┐
  │  video_delay │          │  proj_bond   │   │ seg_display  │
  │ 延迟 8行+8像素│          │ ① 整帧 hist_x[x]++ / hist_y[y]++ │
  │ (原图对齐)    │          │ ② 帧末扫 hist_x → 最左/最右亮栏  │
  └──────────────┘          │ ③ 再扫 hist_y → 最上/最下亮列    │
        │ img_d             │ ④ 圆形先验 → 边界框/圆心/瞄准点  │
        │                   └──────────────┘   │             │
        │                           │ bl/br/bt/bb/cx/cy     │
        │                           ▼                       │
        │                   ┌──────────────┐                │
        │                   │ overlay_box  │ 红色圆环 +      │
        │                   │              │ 瞄准点十字      │
        │                   └──────────────┘                │
        ▼                           │ draw                  │
  ┌────────────────────────────────────────────────────────┐│
  │ 显示合成：draw? 红环/十字 : (纯二值? 黑白 : 原图变暗+命中处原色) │
```

### 四个关键设计决定

**1. 为什么用「双投影」而不是 dart 的 `FindBond.v`（连通域标记 CCL）**

靶标只有**一个**大绿圆，这个特性让「框住它」只需要两个 1D 直方图：

- 资源：两个 `800×10bit + 480×10bit` 的 LUTRAM（实测 210 个 LUTRAM），
  没有等价类合并、label 回收、256 卷标 BRAM、卷标 FIFO 这些容易出鬼的逻辑
- 除错：两个直方图的数值可以直接看，门坎调不对一眼就看得出来
- 时序：X 与 Y 在**同一帧**内算完，框不慢帧

dart 的 `FindBond.v` 是完整 CCL（256 标签 + 64bit BRAM 存每块 `{top,bottom,left,right,num}` +
卷标 FIFO + 帧末扫全部标签取面积最大），能同时处理多个目标。
本工程只需要单目标，所以用轻量替代；若之后要做多目标，直接照 `FindBond.v` 移植即可。

**2. 形态学窗口是「右下角对齐」，所以要补延迟**

`morph_nxn` 的窗口是 `window(x,y) = din(x-N+1..x, y-N+1..y)`，输出的空间位置比输入往右下偏移。
两级串接（膨胀+腐蚀）共偏移 `N-1 = 8` 行/像素，所以：

- 二值图在屏幕上会整体往右下偏 8 像素
- `video_delay` 把**原图也延迟 8 行 + 8 像素** → 屏幕上原图与二值图完全对齐
- 圆环与瞄准点十字用同一套像素串流坐标，所以环一定贴着看到的绿圆

> 这样做的代价是 `video_delay` 需要 `8 行 × 800 × 16bit` 的 LUTRAM（实测 1664 个 LUTRAM）。
> 想省资源可以把 `MORPH_N` 改成 5（延迟变 4 行+4 像素）。

**3. 投影取「外沿」而不是「最长区间」**

旧版取「hist 连续 >= 门坎的最长区间」。问题是：LCD 面板有光泽，镜面反射会在灯上打出一条
**横贯的白色洞**（白色判不出绿）。洞上方的亮像素和下方的亮像素会被切成两段，取到的那段
高度只有原来的一半 —— 框变小、圆心整体上移，看起来就是「识别不到了」。

改成「第一个 / 最后一个 >= TH_MIN 的位置」就只看外沿，中间的洞完全无影响。
代价是对「两块分开的绿块」更敏感（会被串成一个大框），所以形状校验里的
**宽高比 + 峰值高度** 必须留着。（实测数据见第 12 节。）

**4. 圆环用平方比较，不开根号**

`d2 = dx² + dy²`，环上 ⇔ `r_in² <= d2 <= r_out²`。两个平方用组合乘法，Vivado 推断成 4 个 DSP48
（`overlay_box` 一个模块就用掉全部 4 个：`r_in²`、`r_ou²`、`dx²`、`dy²`）。7A35T 有 90 个 DSP，绰绰有余。

## 3. 双投影为什么能框住圆（数学推导）

设绿色圆在**二值图坐标**（即已经含形态学 +8 偏移）下是圆心 `(Cx, Cy)`、半径 `R` 的实心圆。

**X 直方图**：第 `c` 栏的亮点数

$$h_x(c) = \#\{y : (c-C_x)^2 + (y-C_y)^2 \le R^2\} = 2\sqrt{R^2 - d^2} + 1,\quad d = c - C_x$$

（离散弦长）。`h_x(c) >= \mathrm{TH\_MIN}` 的解集是一个**连续区间** `|d| <= d_{\max}`，
其中

$$d_{\max} = \sqrt{R^2 - \left(\tfrac{\mathrm{TH\_MIN}-1}{2}\right)^2}$$

所以「最宽的连续亮栏 run」= `[C_x - d_max, C_x + d_max]`，取宽度

$$W = 2\,d_{\max} + 1$$

同理 Y 方向 `H = 2 d_max + 1`。

**内缩量**：`R = 100`、`TH_MIN = 4` → `d_max = sqrt(100² - 1.5²) = 99.99` → `d_max = 99`（整数）。
于是

```
bl = 408 - 99 = 309 ,  br = 408 + 99 = 507 ,  W = 199
bt = 248 - 99 = 149 ,  bb = 248 + 99 = 347 ,  H = 199
```

也就是说，**框比圆的实际直径各往内缩了 1 像素**（门坎把弦长 < 4 的边缘栏排除了）。
这是「用直方图门坎找边界」这类方法的固有特性，不是 bug。

（外沿投影的实际条件比上式高强一点：取的是「第一个/最后一个 `h_x >= TH_MIN` 的栏」，
对单一凸块而言结果一样；但对于被眩光打洞的块，外沿不受洞影响。）

**峰栏高度**：`max h_x = h_x(C_x) = 2R + 1 = 201`（圆的正中栏弦长 = 直径）。
这个值可以拿来当「这个 run 到底是圆还是横条」的判据（下节）。

## 4. 圆形先验校验（挡掉反光块 / 杂色块）

判定有效需要**同时**满足四条：

| # | 判据 | 表达式（`proj_bond.v`） | 挡掉什么 |
|---|---|---|---|
| 1 | 够大 | `bw >= MIN_SIZE && bh >= MIN_SIZE` | 小碎点 |
| 2 | 不太扁 | `bw <= 2*bh && bh <= 2*bw` | **又宽又扁的反光横条**、左右分开的两块 |
| 3 | 峰栏够高 | `2*xp_best >= bh` | 上下 / 斜对分开的两块 |

判据 3 的物理意义：圆的正中栏弦长 = 直径 = 高度，所以 `xp ≈ H`。
用外沿投影时 `bh` 是「整体外沿」，而 `xp` 是单栏的最高值；
若框其实是「两块分开的绿块」被外沿串成，`xp` 会远小于 `bh`。

> `tools/model_morph.py` 的第 4 组测试就是拿两颗分开的圆去验这三条：
> 左右分开（w=479 h=79）、上下分开（w=79 h=339）、斜对分开（w=279 h=239 peak=61）
> —— 三种都会被挡掉（`ok? False`）。

> 为什么需要这些？因为 LCD 面板有光泽，环境光按**镜面反射**射进镜头时会出现大块眩光。
> 眩光本身是白的（`G-R ≈ 0`）通常过不了颜色判据，但它会**打洞**、也会把整幅画面的曝光/白平衡拉走。
> 加上形状先验之后，即使颜色判据被拉偏，形状不对的块也不会被当成靶标输出。

## 5. 形态学「右下角对齐」的精确推导

设输入二值图 `I` 是实心圆（圆心 `C`、半径 `R`）。窗口约定 `win(x,y) = [x-N+1, x] × [y-N+1, y]`：

1. **膨胀**：`D(x,y) = 1` ⇔ 窗口内存在 `I=1`
2. **腐蚀**：`E(x,y) = 1` ⇔ 窗口内全部 `D=1`

`E(x,y)=1` ⇔ 对窗口内每个 `(u,v)`，都存在 `(p,q) ∈ [u-N+1,u]×[v-N+1,v]` 落在圆内。
对实心圆，这个「最近点」就是把 `C` 的各分量夹到该方框上取到的点。当 `C` 在方框的左上方时，
最近点就是方框的左上角 `(u-N+1, v-N+1)`；而它到 `C` 的距离随 `(u,v)` 向右下单调增大，
所以最坏情况取在 `(u,v) = (x,y)`：

$$E(x,y) = 1 \iff \left|(x-N+1,\; y-N+1) - C\right| \le R$$

也就是说：**`E` 就是原圆整体往右下平移 `N-1`，半径不变**。

这正是测试台期望值的来源：原图圆心 `(400,240)`、`R=100`
→ 二值图圆心 `(408,248)`、`R=100`（半径没缩水，只平移）。

> 这个结论对任何凸集都成立（推导只用到「最近点取在角落」），所以方形灯条的情况同样是纯平移
> ——旧版打靶纸的期望值 `208 = 200 + 8` 也是这么来的。

## 6. 时间关系（重要）

| 事件 | 时机 |
|---|---|
| 像素累积到 `hist_x[]` / `hist_y[]` | 有效显示行（消隐期不算；`y > Y_GUARD` 才算） |
| 扫 `hist_x` 找最宽栏 run | `rd_vsync` 脉冲后，**801 拍**（`WIDTH+1`，多一拍收尾最后一个 run） |
| 扫 `hist_y` 找最长列 run | 接着 **481 拍**（`HEIGHT+1`） |
| 合计 | 约 **1283 拍**；垂直消隐有 `1056 × 45 ≈ 47520` 拍，时间非常宽裕 |
| 边界框出现 | **第 1 帧末**（X 与 Y 同帧算完，不像旧版要等 3 帧） |
| 0 FPS 时的重置 | 每帧末 `S_LATCH` 出结果后回 `S_IDLE`，`de` 一来就继续累加下一帧 |

状态机：`S_IDLE`（累加）→ `S_SCANX`（扫栏）→ `S_SCANY`（扫列）→ `S_LATCH`（出结果）→ `S_IDLE`。

**直方图的清除**就搭在扫描那一趟：扫 `hist_x` 时顺便把读过的地址写 0，扫 `hist_y` 同理。
这样每个直方图都只有**单一写埠**（`we/addr/data` 用 mux 合成），Vivado 才愿意推断成 LUTRAM。

## 8. 按键 / LED / 数码管

按键在板上是**低电平有效**（按下 = 0），LED **低电平点亮**，数码管位选低电平选通、段码低电平点亮。

绿色判据有**三个**门坎，所以 `key[0]` 改成「选哪一个」，`key[1]`/`key[2]` 对选中的那颗做加减：

| 按键 | 脚位 | 功能 |
|---|---|---|
| `key[0]` | T1 | 循环选择要调的门坎：`TH_G` → `TH_G-R` → `TH_G-B` → `TH_G` |
| `key[1]` | U1 | 当前选中的门坎 +8（饱和到 255） |
| `key[2]` | W2 | 当前选中的门坎 −8（下限 0） |
| `key[3]` | T3 | 显示模式切换（0 = 原图变暗+标记；1 = 纯二值图） |

| LED | 脚位 | 意义 |
|---|---|---|
| `led[0]` | R2 | 目前在调 `TH_G` |
| `led[1]` | R3 | 目前在调 `TH_G-R` |
| `led[2]` | V2 | 目前在调 `TH_G-B` |
| `led[3]` | Y2 | 侦测到目标常亮；未侦测到时 1.5 Hz 闪烁（顺便当心跳） |

**6 位数码管**（`dig0` 是最右一位）：

| 位 | 显示 |
|---|---|
| `dig5` | 门坎编号 `1`/`2`/`3`；**小数点亮 = 纯二值图显示模式** |
| `dig4`~`dig2` | 选中门坎的十进制值（`000`~`255`） |
| `dig1`~`dig0` | 目标边界框宽度 ÷ 10；**没侦测到目标时这两位熄灭** |

例：`0 1 0 3 2 7 1 9` → 门坎编号 3、门坎 010、目标宽 199 像素。
位选顺序若与板上相反（`seg_sel[0]` 是最左一位），把 `seg_display.v` 的 `SEG_REV` 设成 `1` 即可。

## 9. 颜色判据（与 dart 的对照）

RGB565 先展成 8bit：

```
r8 = {R5, R5[4:2]}     g8 = {G6, G6[5:4]}     b8 = {B5, B5[4:2]}
```

| 判据 | 条件 |
|---|---|
| 绿 | `(g8 >= TH_G) && (g8-r8 >= TH_G-R) && (g8-b8 >= TH_G-B)` |

这个形式直接借自 dart 工程的 `dart_-fpga/fpga/ip/isp/Threshold_ip/src/Threshold.v`：

```verilog
g_mask <= (G >= THRESHOLD_G);
r_mask <= ((G - R) >= THRESHOLD_G_R);
b_mask <= ((G - B) >= THRESHOLD_G_B);
```

dart 那边是 10bit 影像，测试台给的预设是 `400 / 130 / 130`（`video_stream_tb.sv`），
折算到本工程的 8bit 就是 `100 / 32 / 32`。
三个判断式用的都是**带符号差值**，所以「白」「灰」（`G-R ≈ 0`）不会被误判成绿；
`G >= TH_G` 这一条同时兼任亮度闸，避免暗部噪声。

> dart 的 `Threshold.v` 是 AXI-Stream 界面（`tdata/tvalid/tuser/tlast`），
> 本工程是 `lcd_driver` 那套 `de / x / y` 像素串流，所以只搬判据、重写界面。

**闘 2：相对饱和度（本工程新加，尺度无关）**

```
mx = max(r8,g8,b8);  mn = min(r8,g8,b8);  chro = mx - mn;
100*chro >= mx * REL_SAT_PCT        // 预设 20（%）
```

闘 1 是**绝对**差值，整幅画面变暗或变淡时判据会一起漂移。
相对饱和度只看「色度占最亮通道的比例」：整体变暗/变淡时分子分母同比例缩放，判据不变；
白光眩光 `chro ≈ 0` 会被干脆地排除。两个闸是**串联**的（都要过），
把 `REL_SAT_PCT` 设成 0 就回到纯 dart 判据。

## 12. 反光（眩光）问题：定位与处置

### 症状

把 LCD 屏幕转一点点角度，绿色圆就完全识别不到（或框只剩一半、圆心飘到上面去）。

### 三层原因

1. **相机层（主放大器）**：`rtl/i2c_ov5640_rgb565_cfg.v` 原本让 OV5640 的
   **AEC（自动曝光）+ AGC + AWB（自动白平衡）全部开着**（表里有 `0x3a13=0x43`、AEC 稳定区间
   `0x3a0f/0x3a10/0x3a1b/0x3a1e/0x3a11/0x3a1f`、AWB `0x5180~0x519e`，
   但**没有**写 `0x3503`（AEC/AGC 手动）也没有 `0x3406`（AWB 手动））。
   眩光一进画面就抬高整幅平均亮度 → AEC 缩短曝光 → **全画面一起变暗**；
   反射光是白的 → AWB 推走白平衡 → 绿色判据的差值整体缩小。
   **局部眩光就这样被负回授放大成整个目标消失。**
   > 本工程的处置**不靠关相机自动**（原因见下面「为什么最后没把相机死锁」），
   > 而是把判据改成对这种整体漂移免疫的**尺度无关**形式。
2. **光学层**：LCD 的 γ、对比、色度随视角变化很剧烈（离轴几度饱和度就掉下来，直接穿过固定门坎）；
   眩光本身还有临界角效应（镜面反射光扫过镜头孔径时是阶跃式的，所以是「突然就没了」）。
3. **算法层**：门坎都是绝对值；更关键的是**取「最长连续 run」的投影会被眩光打出的洞切成两半**。

### 对照 dart 的做法

dart 的相机是**固定曝光 + 固定增益**（`io/hikrobot/hikrobot.cpp`：
`ExposureAuto = OFF`、`GainAuto = OFF`、`ExposureTime`、`Gain`；`configs/standard4.yaml` 里
`exposure_ms: 2`、`gain: 16`）。它的传统分割也只用「灰度值 >= threshold」这一类**固定**门坎。

### 已实施的处置

| # | 措施 | 位置 | 成本 |
|---|---|---|---|
| 1 | 颜色判据加**相对饱和度闸**（尺度无关，**抗反光主力**） | `color_seg.v` | 约 72 LUT |
| 2 | 投影从「最长连续 run」改成**取外沿** | `proj_bond.v` | 约 20 LUT（反而更简单） |
| 3 | （选配，**预设关闭**）相机固定曝光 / 增益：`CAM_LOCK_EN = 1'b1` 时写 `0x3503=0x03` + 手动曝光 / 增益 | `i2c_ov5640_rgb565_cfg.v`（`tools/patch_camera_lock.py`） | 0 LUT |

#### 为什么最后没把相机死锁（`CAM_LOCK_EN` 预设 `1'b0`）

dart 的相机是固定曝光，照搬很自然，但**固定曝光值必须按现场亮度标定**。
第一版直接把曝光写死成 `0x0200` 并预设启用，结果该值对现场太小 → 传感器输出一整帧近乎全黑 →
而 `rtl/lcd_driver.v` 里 `assign lcd_bl = 1'b1`（背光常亮），现象就是**背光亮着但屏幕全黑**，
非常像「屏坏了 / 没连上」。同时那一版还写了 AWB 手动增益 `0x3400/0x3401`，
但 OV5640 这组寄存器是 `[9:8]` 还是 `[11:8]` 没有可靠依据（10bit 装不下 `0x400`，
更像 `[11:8]`，即 1x 要写 `0x04`），写错同样导致画面异常。

所以现在的做法是：

- **预设完全不动相机**（`CAM_LOCK_EN = 1'b0`，写 `0x3503 = 0x00`，等同原厂自动曝光），
  抗反光由上面第 1、2 条**尺度无关**的算法措施承担 —— 它们对相机自动曝光 / 白平衡的漂移天然免疫。
- 想要极致稳定性再开 `CAM_LOCK_EN = 1'b1`，并**上电看着 LCD** 标定 `EXP_15_8`
  （太暗加大、过曝减小，大致 `0x0100` ~ `0x2000`），换环境需重标。
- **完全不碰 AWB**（`0x3406` 保持自动），把无法验证的寄存器格式风险直接移除。

### 效果（`tools/model_morph.py` 的独立模型 + `tb_armor_vision.v` 的相位 2）

眩光带横贯圆心（py 225..255，高 31px，白色）：

| 眩光带高 | 旧版「最长 run」 | 新版「取外沿」 |
|---|---|---|
| 0 | h=199, cy=248 ✓ | h=199, cy=248 ✓ |
| 10 px | **h=94, cy=195 ✗** | h=199, cy=248 ✓ |
| 20 px | **h=89, cy=193 ✗** | h=199, cy=248 ✓ |
| 30 px | **h=84, cy=190 ✗** | h=199, cy=248 ✓ |
| 40 px | **h=79, cy=188 ✗** | h=199, cy=248 ✓ |
| 60 px | **h=69, cy=183 ✗** | h=199, cy=248 ✓ |

**眩光带只有 10px 就让旧版的高度从 199 掉到 94、圆心 y 从 248 跳到 195** ——
那就是「转一点点角度就识别不到」的现场。新版直到 60px 都还给出正确的 149/347。

> 实际的 bbox 宽度会随眩光变宽而微微缩小（边缘栏弦长本来就短，被吃掉几个像素就掉到门坎以下）：
> 30px 时 310/506（w=197）、40px 时 311/505（w=195）。这是合理的，不是错。

### 还没做、但建议做的（物理层）

- LCD 贴**防眩光（雾面）膜**，或给镜头加一片与面板偏振方向正交的**偏振片**，
  可以把镜面反射压掉 90%+，这是真正的治本
- 若环境光经常变化：每次换场地重新按亮度调一次曝光（`EXP_15_8` / `GAIN_7_0`）

## 13. 瞄准点：打击点在绿灯上方

### 需求

相机看到的是绿灯，但实际打击点在灯的**上方一点**。两者有一个固定的物理偏移
（设灯直径 `Dt`、打击点比灯心高 `Δh`，拿现有靶纸量一下就有）。

### 推导：不需要额外测距

针孔模型下，同一个 `f`、同一个距离 `D`：

$$
W = f_{px}\cdot\frac{D_t}{D}\;(\text{灯的表观宽度})\qquad
\Delta_{pix} = f_{px}\cdot\frac{\Delta h}{D}\;(\text{打击点的像素偏移})
$$

两式相除，**距离 D 直接消掉**：

$$
\boxed{\Delta_{pix} = W\cdot\frac{\Delta h}{D_t}}
$$

所以只要知道「物理偏移 / 灯直径」这个**无量纲比例**，就能直接从表观宽度算出瞄准点的像素位置，
不需要单独测距 —— 距离信息已经被宽度隐含了。

RTL 里就是一瓣：`aim_y = center_y - (宽度 * AIM_H_Q8) >> 8`，
`AIM_H_Q8` 是 Q0.8 定点，在 `blob_track.v` 里是 **16 位输入埠**（`aim_h_q8`），
所以 UART 写 `0x05` 就能在线微调（见 §17）；默认值由 `armor_vision` 的 parameter 给。

> RM 靶目标实测值：灯直径 **55mm**、打击点在灯心上方 **80mm**
> → `AIM_H_Q8 = round(256 × 80/55) = 372`（= 1.449 倍灯直径），**这就是现在的默认值**。
> 它大于 255，所以字段必须是 16 位 —— 8 位版本会把它静默截断成 116（= 0.45 倍）。
>
> 模拟里 `tb_armor_vision.v` 把主实例钉在 `16'd64`（让瞄准点留在画面内、好比大小），
> 另外建了一个 `u_blob_real`（`16'd372`）专门验证「偏移超出画面时饱和到 0」。

> ⚠️ **位宽坑**：Verilog 里 `a * b` 的结果位宽 = `max(两个操作数位宽)`，**不是两者之和**。
> 写 `wire [AW:0] up = (bw * AIM_H_Q8) >> 8;` 时乘法会被算在 11bit 上：
> `199*64 = 12736` 被截成 448，`>>8` 得 1 —— 瞄准点只抬了 1 像素（测试台当场抓到）。
> 必须先宣告够宽的中间量：`wire [AW+7:0] up_full = bw * AIM_H_Q8;`。

### dart 工程怎么做（对照）

dart 的相机看的也是灯心，另外迭一个**角度**偏移。它的距离是从「目标的表观**面积**」反推的：

```c
// alg_proportional_navigation.c
target->photo_target_area = (w - 8.0f) * (h - 8.0f);   // 减掉图像处理加的 8px 宽
target->photo_target_distance = alg_lookup_table_query(&area_to_distance_lookup_table, area);
```

表定义在 `lib_table.h`（500 点，距离 50cm~1500cm，`area ∝ 1/D²`：50cm 时 2760，52.9cm 时 2457）。
拿到距离后它去做**弹道 / 下坠**补偿（`task_control.c`）：

```c
target_atatact_theta = 30.0f;
target_atatact_theta -= (10.0f/400.0f) * photo_target_distance;   // 距离越远角度越小
```

另外 `alg_proportional_navigation.h` 里还有
`WORLD_VFOV_ADD_ANGLE_RAD_MAX/MIN = 10°/3°`（批注：「世界坐标系目标垂直视场角需要增加的角度
（考虑下降影响）」），也是按距离插值。

**结论：**

| 要补偿什么 | 需要知道距离吗 |
|---|---|
| **目标本身的几何偏移**（打击点比灯高） | **不需要** —— 像素偏移 = `W·(Δh/Dt)`，取的是「宽度」这个距离代理量 |
| **弹道下坠**（飞过去会掉） | **需要** —— 它是**角度**偏移，与距离、弹速都有关；dart 就是靠面积查距离再查下坠曲线 |

本视觉管线只负责前者（也就是使用者问的那一项）。
下坠属于飞控侧，需要时直接把「表观宽度」接过去即可 —— 数码管上那两位
（`目标宽度 ÷ 10`）就是这个量的实时显示。

### 怎么标定 `AIM_H_Q8`

1. 把靶子放在已知距离，读数码管上的「宽度/10」→ 得到 `W`
2. 量出「打击点到灯心的物理距离 `Δh`」和「灯的实际直径 `Dt`」
3. `AIM_H_Q8 = round(256 * Δh / Dt)`
4. 上电后看十字是不是正好落在想打的位置；不对就微调 `AIM_H_Q8`

> 例（RM 靶标）：灯直径 55mm、打击点在灯心上方 80mm → `256 × 80/55 = 372`。
> 此时画面上灯宽 199px → 十字在灯心上方 `199×372/256 = 289` 像素处 ——
> 比环半径（约 100px）大 3 倍，所以十字会落在**红环外面很远**。
>
> ### 取景必须对准打击点，不是对准灯
>
> 偏移是 1.449 倍灯宽，比环半径（0.5 倍灯宽）大得多。若把灯摆在画面正中（`c_y ≈ 240`）
> 而灯宽 200px，瞄准点会被算到 $240 - 289 = -49$，**在画面之外**。所以：
>
> $$1.449\,W \le c_y \le 479 - \tfrac{W}{2} \quad\Longrightarrow\quad W \le 245\text{ px}$$
>
> 推荐灯的表观宽度做 100~130 px（灯心 y ≈ 390~420），瞄准点就落在画面中心。
>
> ### 为什么 `aim_y` 必须用饱和减法
>
> `aim_y <= cy_w - up_t` 是无符号减法：$c_y < \text{up}$ 时会**下溢回绕**到 1024 附近，
> 十字跳到画面底部（看起来像算法坏了）。以前 `AIM_H_Q8 = 64`（偏移 0.25 倍宽）几乎碰不到，
> 换成 372 之后**必然**碰到，所以 `blob_track.v` 改成先补到 19bit 比较再减、小于则输出 0。
> 验证在 `tb_armor_vision.v` 的 `u_blob_real`：372 下 `aim_y` 必须是 **0**，不是 1023 附近。

## 14. 已知限制与后续方向

- **只输出一个目标**：取 X/Y 直方图的外沿，画面同时出现多个绿块时会被串成一个框
  （**会被形状校验挡住 → 不输出**）
  → 需要多目标就要移植 dart 的 `FindBond.v`（256 卷标 CCL + BRAM 存每块结构 + 帧末取面积最大）
- **没有弹道下坠补偿**：只给圆心与瞄准点（目标几何偏移）。下坠是**角度**偏移，和距离、弹速都有关，
  属于飞控侧；dart 用的是「表观面积 → 距离 → 下坠曲线」两步算，本工程已经把「表观宽度」
  放在数码管上，需要时可以直接接过去
- **相机固定曝光是「选配」且预设关闭**：`CAM_LOCK_EN = 1'b0` 时相机保持原厂自动曝光 / 自动白平衡，
  抗反光完全由两条尺度无关的算法措施承担。想要 dart 那种「曝光死锁」的极致稳定性，
  把 `CAM_LOCK_EN` 打开并按现场亮度标定一次（换环境要重标 —— 这是拿通用性换稳定性）
- 其他可延伸：瞄准点经 UART 送给云台 / 加 ILA 观察两个直方图峰值
- 对应《RM飞镖FPGA视觉方案》文件的阶段 1~6 皆已完成（验证对照见第 11 节）

## 16. PL 增强路线图（对标 dart2026）

读过 dart 的 PL 侧（`dart_-fpga`）后的结论：**dart 的 PL 强在「特征提取完整度 + 平台化」，
弱在「自适应与时序」** —— 后者恰好是纯 RTL、没有 PS 的我们最该补的地方。

对比要点：

| 能力 | dart PL | 本专案 |
|---|---|---|
| 二值化 | `Threshold.v`：`G≥T_G && G-R≥T_GR && G-B≥T_GB`（三阈值皆 AXI 寄存器） | `color_seg.v`：**同样三条 + 相对饱和度闸**（多一道，尺度无关） |
| 形态学 | `ExpansionAnd → Expansion → Corrosion` 多级 | 9×9 膨胀 → 9×9 腐蚀（闭运算） |
| 特征提取 | **`FindBond.v` 真 CCL**：256 卷标、每卷标 64bit 结构存 BRAM、并查集重标、累加面积 | **双投影取外沿**：单框、无面积、多目标必挂 |
| 多目标 | `bond_dma.v`：每帧**全部** blob 打包 128bit 写 BRAM + 计数 → PS | 无 |
| 参数下发 | AXI-Lite 寄存器 + Linux 驱动，执行时可改 | 按键 + 数码管，手动 |
| 结果上报 | IRQ + AXI 回读 + DMA 列表 → PS → 飞控 | 只有 LCD / 数码管 / LED（给人看） |
| 除错 | VDMA → DDR + JPEG 编码 + WiFi 推流 + `system_ila` | 只有 LCD |
| **时序滤波 / 跟踪** | **无** | **无** → 两边都没，是本项目的差异化空间 |

### 阶段与状态

每阶段都要过三道关：xvlog 无错 → xsim 自检全过 → 综合 0 error / 0 warning / 0 latch。
新功能一律带 `XXX_EN` 开关，**默认值保持既有已验证行为**。

| 阶段 | 内容 | 状态 |
|---|---|---|
| P0 | 仪表盘（fps / 帧周期 / 帧行数 / 掩码像素数 / 命中率）+ `mark_debug` 供 ILA | **已完成** |
| P1 | UART 结果输出（`valid, cx, cy, ax, ay, w, h, checksum`）给云台 / 飞控 | **已完成** |
| P2 | 执行时寄存器文件（UART 写参数，免重新综合） | **已完成** |
| P3 | 团块跟踪（行程级，取代双投影）+ 每块面积 + 形心 + 圆度 | **已完成**（见下方说明） |
| P4 | 时序门控 + 持久性 + α-β 跟踪 | **已完成** |

### P9：为什么远处的灯「屏幕上有高亮却认不到」

现场症状：把绿色圆灯拉远，LCD 上仍能看到高亮（那是 `color_seg` 的掩码本身，显示走 `mask_d`），
但 `bond_valid = 0`、没有红圈、没有瞄准点。

根因在 `blob_track.v` 的选块循环：

```verilog
if(r_used[mi] && (r_area[mi] >= MIN_AREA))   // MIN_AREA = 400，而远灯只有几十像素
```

**面积不够的块连「候选」都不是，最大的那块也被丢掉**，于是整帧 `best_any = 0`。
和反光无关、和阈值无关 —— 就是一条写死的面积门坎。

修法：两级门坎。严档（>= `MIN_AREA`）优先，没有严档时接受「面积 >= `min_area_lo` 且形状合理」的块：

```verilog
ss_ok = (tw <= (th << ASPECT_SHIFT)) && (th <= (tw << ASPECT_SHIFT))   // 长宽比 <= 8:1
     && ((r_area[mi] << 2) >= tp_c);                                   // 填充率 >= 1/4
```

形状合理性**只作用于宽松档**：面积小的时候填充率 / 长宽比对噪声极敏感（一个 3x3 的灯
fill 就是 256），所以不能用圆的 π/4 去卡小目标，只挡「细长条」和「空心块」。

- `min_area_lo` 预设 **8**（非常灵敏：只要有一小撮绿像素就报出来），UART `0x04` 可执行时调大
- `min_area_lo = 0` → **关闭宽松档，行为与旧版逐位一致**（逃生开关）
- `blob_far` / 上报 flags.b6 会告诉上层「这一帧是小而远的目标」

副作用与取舍：门坎放低后，画面里的绿色噪点也可能成为候选。缓解手段有四层：
相对饱和度闸（尺度无关）、形状合理性、取面积最大的那块、以及 `TRK_EN`（门控 + 持久性）。

### P10：预测打中位置（lead）

舵机跟踪要的是「灯**现在**在哪」；要打中要的是「飞镖**飞到时**灯在哪」。
两者差一个 `飞行时间 × 目标速度`，距离越远 / 目标越快差得越多。

```
v_q4 <= v_q4 + (( (cx - cx_prev)<<4 - v_q4 ) >>> 2)      // α-β 速度估计，Q4
pred  = clamp( cx + ((v_q4 * LEAD_Q4) >>> 8) )           // 外推，饱和到画面内
pay   = pred_y - up,   up = bw * AIM_H_Q8 / 256           // 几何偏移，和 blob_track 同一公式
```

- 两者都走 `raw_*`（不经 `TRK_EN` 门控），**不加延迟**：舵机跟踪要的就是快
- 历史不足（连续有效 < 2 帧）/ 关闭 / 本帧无效时 `pred_ok = 0`，输出**直接镜像当前帧**
  → 静止目标下开 / 关预测的输出逐位一致，不会动到已验收的行为
- `LEAD_Q4` 预设 64（= 4.0 帧，30fps 下约 133ms），UART `0x0A` 可调；
  知道弹速和距离就把它换算成帧数填进来（`LEAD_Q4 = 16 × 飞行时间 / 帧周期`）
- LCD 上：红色十字 = 当前几何瞄准点，**黄色十字 = 预测瞄准点**（只在 `moving` 时画）

> 为什么不直接用 `TRK_EN` 的 α-β 速度：那条路径有 `HIT_N` 帧的确认延迟（门控 + 持久性），
> 对舵机来说太慢。预测模块自己做一套轻量速度估计，两者互不干扰。

### 两处刻意偏离原方案（重要）

**P3：用「行程级团块跟踪」而不是 dart 的「256 标签逐像素 CCL + 并查集」**
dart 的 `FindBond.v` 需要一条 800 深的标签行缓冲 + 256 项 64bit 结构体表 + 重标表，
还要一套 3 级流水在同一拍里解决左右/上下标签冲突。本专案的 `blob_track.v` 改成：
每行抽出 mask 的**连通行程**，与 4 个团块记录做「水平区间重迭 + 行相邻」匹配，
命中多个就合并（面积/矩相加），都没命中就新建记录。
输出（每块外框 + 面积 + 形心 + 圆度 + 数量）与 dart 那套**完全一致**，但不需要逐像素
卷标 RAM 和并查集表，逻辑量约为前者的 1/4，也更好在测试台里逐项验证。
代价：最多同时跟踪 `K=4` 个团块（对「一个大的灯」这种靶标绰绰有余）。

另外这里**不需要 FIFO 和状态机**：`emit` 只在 mask 由 1 变 0（或行尾收尾）时产生，
两次 emit 至少隔 2 拍，而匹配判定 + 记录更新是纯组合的，正好在 emit 那一拍吃完 ——
一拍一个行程、零丢弃、无吞吐瓶颈。

**P8：OSD 第四行放填充率而不是距离**
面积反推距离要开根号，而且相机/镜头没标定之前绝对值没有意义。
所以 F3 显示 `fill_q8`（圆的理论值约 201，一眼看出圆不圆）。
要距离请拿 F2 的面积在上位机里算，那里做 sqrt 是免费的。

### 边界定义的变化（导致旧测试台的期望值要放宽 1~2 像素）

旧的 `proj_bond` 取直方图外沿时有 `TH_MIN=4` 的裁剪：边界上只有 1~3 个亮像素的
行/列会被丢掉。新的 `blob_track` 报的是**全部亮像素的真实外延**，所以外框会宽 1~2 像素
（圆心不变，仍是 408/248）。这不是错误而是定义变准了，因此测试台对边界改用
`chk_near(±2~3)`，而圆心 / 瞄准点 x / 有效性仍然精确比较。

## 17. 对外界面：UART 上报与参数写入

### 结果上报（P1，`result_frame.v`）

每 `TX_DIV`（预设 8）帧发一条定长帧，115200 8N1。**v2 = 24 字节**（字节 0~14 的含义与 v1 完全一致）：

| 字节 | 内容 |
|---|---|
| 0 / 1 | `0xA5` / `0x5A` 帧头 |
| 2 | flags：b0=`valid`、b1=`adapt_ok`、b2=二值显示、b3=保留、b4=`pred_ok`、b5=`moving`、b6=`far_small`、**b7=1（v2 标记）** |
| 3 / 4 | 圆心 x（16bit，高/低） |
| 5 / 6 | 圆心 y |
| 7 / 8 | 瞄准点 x（**当前帧**的几何瞄准点，语意同 v1） |
| 9 / 10 | 瞄准点 y |
| 11 | 外框宽（饱和到 255） |
| 12 | 面积 >> 7（饱和到 255） |
| 13 | `fill_q8` 填充率（圆约 201） |
| 14 | 本帧合格团块数 |
| 15 / 16 | `vx_q4` 速度估计 x（Q4 有符号，**16 = 1 px/帧**） |
| 17 / 18 | `vy_q4` 速度估计 y |
| 19 / 20 | 预测灯心 x（LEAD 帧之后） |
| 21 / 22 | 预测灯心 y |
| 23 | checksum = byte2..byte22 逐字节异或 |

> **云台 / 飞控要打提前量，就指向** `(px, py - w × AIM_H_Q8 / 256)`（`AIM_H_Q8 = 372` 是常数）。
> 只想知道「现在瞄哪里」就继续用 `ax/ay`，语意没变。
>
> **为什么校验和从 byte15 搬到 byte23**：v2 的 flags.b7 置 1，旧解析器用 v1 的
> 「byte2..byte14 异或 == byte15」必然验不过 → 旧程序会**安全地丢弃**新帧，
> 而不是把 `vx_q4` 当成校验和读出垃圾数据。`tools/uart_parse.py` 已同时支持两种长度，
> 并且会把 Q4 速度换算成 px/帧 显示。

    > **已接好引脚**：`uart_rxd` = **U5**（input）、`uart_txd` = **T6**（output），
    > 电平 LVCMOS33，取自《达芬奇开发板IO引脚分配表》，已在 `pin.xdc` 里约束。
    > （表上另有 `uart2_txd`=R19 / `uart2_rxd`=P19，那是 ATK 模块接口，未使用。）
    >
    > PC 端解析：`python tools/uart_parse.py COM3`（需 pyserial）；
    > 脱机解析：`python tools/uart_parse.py --hex "A5 5A ..."`；
    > 下发参数：`python tools/uart_parse.py COM3 --set 0x07 0x01`。

### 参数写入（P2，`reg_file.v`）

每条命令 **4 字节**：`0xAA  addr  data  (addr ^ data)`，校验不过整条丢弃。

| addr | 参数 | 预设 |
|---|---|---|
| `0x00` | `TH_G` | 100 |
| `0x01` / `0x02` | `TH_G-R` / `TH_G-B` | 32 |
| `0x03` | `REL_SAT_PCT` 相对饱和度闸限（>100 夹到 100；**0 = 关闭该闸**） | 20 |
| `0x04` | **宽松档最小面积** `min_area_lo`（0 = 关闭宽松档，回到「只认 >= 400 像素」） | 8 |
| `0x05` | `AIM_H_Q8` 低 8 位（小数部分） | 116 |
| `0x06` | `RING_T` | 2 |
| `0x07` | `CTRL`：b0=自适应 b1=中值 b2=曝光死循环 b3=二值显示 b4=OSD **b5=速度预测** | 0（全关） |
| `0x08` | `GATE` 门控半径 | 96 |

> **`0x03` / `0x04` 以前是死寄存器**：`reg_file` 一直有这两个地址，但 `armor_vision.v`
> 里只有宣告、没有接进 `color_seg` / `blob_track`（和当时 `0x05` 的坑一样：文件写了、程序没接）。
> 这次一起接上了：`0x03` 现在真的改相对饱和度闸限，`0x04` 改成宽松档最小面积。
> `0x08`（`GATE`）/ `0x09`（`ADAPT_PCT`）/ `0x06`（`RING_T`）仍然是 parameter-only，
> 写了不会生效 —— 要用的话按同一套路径接即可。
> `MIN_SIZE` 这个 parameter 目前已无消费者（形状校验改由 `blob_track` 内部的
> 长宽比 + 填充率负责），保留只是为了不破坏既有例化。

> **`0x05` 的位宽说明**：`AIM_H_Q8` 是 16 位（RM 靶标要 372），而 UART 寄存器一次只传 1 字节，
> 所以协议定为：**`0x05` 只覆盖低 8 位（小数部分），高 8 位沿用 parameter**。
> 372 = `16'h0174` → 高 8 位 1、低 8 位 116，而 `reg_file.v` 的 `r_aim_h` 复位值也正是 116，
> 所以「只写别的阈值寄存器」不会动到瞄准高度；写 `0x05` 可在 1.0~1.996 倍之间微调
> （步长 1/256 = 0.0039 倍灯直径）。要在线设到 > 1.996 倍就改 `armor_vision.v` 的 parameter 重新综合。
>
> 早期版本这里有个**文件与程序不符**的坑：文件写了 `0x05` = `AIM_H_Q8`，
> 但 `rf_aim_h` 在 `armor_vision.v` 里只宣告、没接进 `blob_track`（等于写了没用）。

> 接不了运行时寄存器（xvlog 会报 `'aim_h_eff' is not a constant`）。

所以**预设行为与加 UART 之前一模一样**，这也让它适合当回退手段。

### P0 细节（`vision_stat.v`）

纯观测模块，不参与任何判决、不改画面。`vsync` 一律走**边沿**判定：
`tb_armor_vision` 里 `vsync` 是「宽 101 拍的电平」而非单拍脉冲，真机 `rd_vsync` 形态也不好假设；
若直接拿电平当条件，宽 `vsync` 会把计数器反复清零，`frame_cyc` 恒为 0。

- **上升沿** = 帧起点 → 锁存上一帧统计量并清零
- **下降沿再晚一拍** = `frame_tick`，此时 `proj_bond` 本帧结果已稳定（命中率就在这里采样）

`fps` 用「1 秒窗口数 `vsync` 个数」实现，省一个除法器，而且给的是**真实平均值**
（帧周期抖动时比瞬时值更有参考价值）。但仿真里不可能真跑 1 秒，
所以测试台**另建一个 `CLK_FREQ = 2×(H_TOTAL×V_TOTAL)` 的实例**，窗口正好等于 2 个帧周期
→ `fps` 应恒为 2，可精确断言（比断言 1 强，能排除「计数器卡住」的巧合）。

资源：几个饱和计数器，约 120 LUT / 100 FF，**0 BRAM**。
P0 阶段这些统计量还没有下游消费者（UART 在 P1 才接），所以例化上加了
`dont_touch` 把实例钉住，否则综合器会整块优化掉、`mark_debug` 抓不到东西；P1 之后可以拿掉。

从红蓝版升级到绿色版：`python tools/patch_green.py`（可重复执行，已套用过）。

## 20. 弹道补偿（P11）：由表观宽度反推距离与下坠

### 需求

飞镖飞行过程中会下坠（5m、弹速 20m/s 时 t=0.25s，自由落体已经 30cm），
所以「瞄准点」不等于「灯心 + 几何偏移」，还要再抬一个下坠量。
PL 没有测距仪，唯一可用的距离线索是**表观宽度 w**。

### 推导：两件事都只是 1/w

相机焦距（像素）`f_px = 2570`（第 13 节推过）、靶标灯直径 `D = 55mm`：

```
dist_mm = f_px * D / w = 141350 / w        ->  dist_cm = 14135 / w
```

下坠是世界坐标的量，但要补在【像素】上：

```
dist_m    = dist_cm / 100
t         = dist_m / v0                 (v0 = 弹速)
drop_m    = g*t^2/2
px_per_mm = w / D                     <- 这一项也含 w
drop_px   = drop_m * 1000 * px_per_mm
```

把 `dist_m ∝ 1/w` 代进去，w 只剩一次幂：

```
drop_px = 4454.5 / w                  (v0 = 20 m/s)
```

**所以两张 256 项的表都只是 1/w** —— 零除法、零乘法、时序零风险。

换弹速也不用重新综合：写 UART `0x0B` 的 `DROP_SCALE`（Q8，255 = 20m/s）：

```
DROP_SCALE = round(256*(20/v0)^2) - 1
20m/s -> 255     25m/s -> 163     30m/s -> 113     15m/s -> 454
```

### 实现

`rtl/ballistic.v`（两张表由 `tools/gen_ballistic_lut.py` 生成，改公式就重跑那个脚本）：

```
dist_cm = ROM_DIST[bw]                                (bw > 255 饱和；bw < 8 视为无效)
drop_px = (ROM_DROP[bw] * (DROP_SCALE+1)) >> 8
fx      = 预测灯心 x
fy      = 预测灯心 y - (w*AIM_H_Q8/256) - drop_px     (单调饱和，减不够就取 0)
```

`dist_ok` = 有目标且宽度在表内（`bw >= 8`），上报在 flags.b3。

### 与速度预测的关系

`aim_predict`（提前量）与 `ballistic`（下坠）是两个独立的修正，串在一起：

```
预测灯心 -> 几何偏移（打击点在灯上方）-> 下坠补偿 -> fx / fy
```

**云台直接用 `fx/fy`**，不用自己重算。中间量（cx/cy、px/py、dist_cm、drop_px）也全都上报，便于调试。

### 校准

1. `f_px` / `D` 写在 `tools/gen_ballistic_lut.py` 头部 —— 改完重跑脚本 + 重新综合；
2. 弹速用 UART `0x0B` 在线调（**不用重新综合**），打几发看落点偏移再微调；
3. 想知道 `f_px` 到底是多少：把灯放在已知距离，读数码管/OSD 上的宽度，
   `f_px = w * dist_mm / 55`。

## 21. 上报协议 v3 与“死寄存器”清账（P11）

上报帧从 16 字节（v1）升到 **34 字节（v3）**：新增速度、预测灯心、距离、下坠、
最终瞄准点、**帧序号**，并把单字节异或换成 **CRC-16/CCITT-FALSE**。

### ⚠️ 发送中被重复锁存（P12 期间被软件 CRC 抓出来的致命 bug）

症状：收到的帧 `seq = 0x0D`，但 CRC 却是 `seq = 0` 那一帧的（`0x8B12`）；第二帧 `seq = 0x1C (28)`、
CRC 又是 `seq = 15` 那一帧的（`0x7AFD`）—— **同一帧里 `seq` 与 CRC 来自不同的帧**。

根因：`wire tx_now = frame_tick && (divcnt == TX_DIV - 1);` 是**电平型**触发，
而负载锁存块写的是 `else if(tx_now) ...`、**没有判 FSM 状态**：

```verilog
else if(tx_now) begin        // ✗ 发送途中会被重复锁存
    b[2] <= flags; ... b[31] <= seq[7:0];
    seq   <= seq + 16'd1;
end
```

一帧的发送时间（34 字节 @115200 ≈ 74,000 拍）远大于 `frame_tick` 周期（5,000 拍），
发送途中 `tx_now` 又高了十几次 → 负载被重复锁存、`seq` 被多加
（实测差 **15** = 74000/5000 ✔ 对得上）。CRC 是在帧头锁存后算好并冻结的，
传出去的 `seq` 却是后来又锁存的 → **接收端按 CRC 校验必然丢帧**。

**更糟**：真实工程里 `cx/cy/w/dist` 每帧都在变，中途重复锁存会把**两帧的数据混成一帧**
（测试台输入是常量，所以只暴露了 `seq` 这一项）。修法：

```verilog
else if(tx_now && (state == S_IDLE)) begin   // ✔ 只在「帧起始」那一拍锁存
```

（`S_IDLE` 在 `tx_now` 那一拍本来就跳 `S_CRC`，两者同拍，CRC 用的仍是新负载。）

> **教训：要拿「testbench 自己算的软件 CRC」去对拍硬件的 CRC。**
> 原来是拿一个固定魔数 `0x8B12` 去比 —— 它只验了「CRC 算法对不对」，
> 抓不到「CRC 与 payload 不是同一帧」这种错。
> 另外，直接把收到的 68 个字节 `$write("%02x")` 印出来（而不是只印 `chk` 结果），
> 是这次定位的关键：一眼就看到 `... 00 b2 0d 8b 12`（`seq=0x0D` 配 `0` 的 CRC）。

> 一路踩到的同一个坑：「文档写了、代码没接」——`0x05 rf_aim_h`（旧）、
> `0x03/0x04`（P9 修）、`0x06/0x08/0x09`（P11 修）。
> **自查法**：全局搜 `rf_xxx`，只出现「声明 + 例化联机」2 次的就是死的。

## 19. 时序：50MHz 下的 setup 违例与三级流水

### 现象

P9（两级面积门坎）之后跑 implementation：

```
[Timing 38-282] The design failed to meet the timing requirements.
   WNS -5.242 ns   TNS -48.373 ns   Failing Endpoints 10 / 46587
```

### 定位（两个小工具）

```
python tools/timing_peek.py          # 读 impl_1 的 timing_summary_routed.rpt，抽重点
vivado -mode batch -source tools/timing_peek.tcl -nojournal
                                     # 直接在 routed checkpoint 上列【所有 slack < 1ns】的路径
```

`timing_peek.tcl` 是关键：summary 报告只有「最差的 10 条」，修完一条后下一条如果只是
`-0.1ns` 就要再等十几分钟重跑实现。一次把所有逼近极限的路径列出来，才能一轮修完。

结果非常干净：

| 路径 | slack |
|---|---|
| `u_blob_track/r_l_reg[0][6]/C` → `u_blob_track/aim_y_reg[9:0]/D`（10 位 = 10 个端点） | **-5.242 ns** |
| 其余全部（含 MIG / DDR3 / LCD / 相机路径） | ≥ **+0.98 ns** |

时钟是 `clk_out2_clk_wiz_0`（**50 MHz，20 ns**），不是像素时钟的 25 MHz —— 这条管线的
时序预算只有 20 ns，不是 40 ns。

### 根因

P9 把形状合理性检查（4 个候选各一个 `w*h` 乘法 + 长宽比/填充率比较 + 两级优先树）
塞进了原本「选块 → 几何换算（`bw × AIM_H_Q8` → 饱和减法 → `aim_y`）」的**同一条**组合链：

```
r_l_reg[0] ─┐
            ├─ 4×(w*h 乘法 + 比较 + 优先树) → best_i → mux → bw_w → ×372/256 → 饱和减法 → aim_y_reg
r_area      ─┘                              25.160ns（logic 14.313 + route 10.847）
```

模拟看不出来（`synth_check_vision.tcl` 是 **out-of-context 综合，没有任何时序约束**），
只有 implementation 才报。

### 修法：三级流水（`tools/patch_blob_timing.py`）

```
级 0（组合）  形状合理性：4 个候选并行 w*h + 比较            → shp_now
级 1（寄存器）shp_ok_r      <- shp_now      ← 乘法移出选块路径
级 2（寄存器）best_i_r / best_any_r / best_far_r / cnt_r   <- 选块结果
级 3（寄存器）sl_r/sr_r/st_r/sb_r + sa_r/sx_r/sy_r + sany_r/sfar_r/scnt_r
级 3 之后（组合）cx_w / cy_w / bw_w / up_t / ay_s → 在 vsync 下降沿采样
```

**为什么加几拍完全不会改变行为**（这是不动逻辑就能修时序的关键）：

- 团块记录只在一帧里 `emit` 时才改变，而结果只在 **vsync 下降沿**取用 —— 中间隔着几百拍；
- 记录清空同样发生在 vsync 下降沿那一拍，而输出端读的是**清空之前**就已经打进流水线的值
  （nonblocking 语义下，同一拍的 `<=` 读到的是该拍之前的状态）；
- 所以只要「最后一次 emit → vsync 下降沿」≥ 流水级数（3 拍），时序上是等价的。

实测：**90 项自检逐项不变**（`ALL CHECKS PASSED`），包含远/小目标、速度预测、UART v2。

### 教训

- 这种「一帧内准静态」的数据（团块记录、选块结果、几何参数）**可以随便打拍**，
  代价只是一次性的几十个 FF —— 这是纯 RTL 设计里最便宜的时序修法；
- 相对地，**逐像素**的数据流（行缓冲、形态学、投影）不能乱加拍，那要算好对齐；
- 新增逻辑后要盯住「这一条组合链有多长」，`w*h` 这种乘法尤其危险；
- OOC 综合绿灯 ≠ 时序收敛，两件事都要跑。

## 18. 两个「仿真过、实现挂」的坑（多驱动网络）

xsim **容忍**同一个 reg 被多个 always 块驱动（它自己挑一个，跑起来「看起来正常」），
Vivado 则直接拒绝：

```
[Synth 8-6859] multi-driven net on pin u_armor_vision/u_chroma_hist/hgb[255][19] ...
[DRC MDRV-1] Multiple Driver Nets: Net .../Q[0] has multiple drivers (99 more like this)
[Vivado_Tcl 4-78] Error(s) found during DRC. Opt_design not run.
```

> 结论：**仿真全过 ≠ 能实现**。新增任何 always 块之后，都要回头确认自己写的 reg 没有第二个驱动源。

### 两处病灶

| 档案 | reg | 症状 | 修法 |
|------|-----|------|------|
| `chroma_hist.v` | `hgr` / `hgb` / `total` | 直方图「扫描时清零」与「工作时累加」各写一次；`total` 也是两块都写 | 写口合成**单一写埠**：`hist_we = scanning \| (de & ~scanning)`，`h_addr`/`h_addr_b` 用 mux 在扫描地址与像素地址间选，下一个值 `hgr_nx`/`hgb_nx` 也 mux 好，只留**一个**时序块写数组；`total` 只由扫描 FSM 驱动 |
| `osd_text.v` | `conv_done` | 转换 FSM 里置 1/清 0，数字刷新块里用完又清 0 | 只留 FSM 驱动，并改成单拍脉冲 `conv_done <= (cv_state == CV_SAVE) && (cv_sel == 2'd3);`；刷新块**只读不写** |

`osd_text.v` 的**复位分支**里也有一行 `conv_done <= 1'b0;` —— 那是**同一块内**的赋值，合法；
删的时候要连带后一行 `nd0 <= ndig(b0_bcd);` 一起当锚点，否则会误删。

脚本：`python tools/patch_fix_multidriver.py`（纯 ASCII 锚点 + 回读比对，可重复执行）。

### 自查方法

1. 每个时序块写的 reg，全局搜寻它一共出现几次 `<=` 赋值；跨到 >1 个块就是多驱动。
2. 内存（数组）最容易踩：「清零」与「累加」写在**同一个** always 的两个 `if` 里是合法的，
   写在**两个** always 里就是多驱动。而且多写端口还有第二个副作用 —— **挡掉 RAM 推断**（见 §7）。
3. 最终验收只能靠综合：`vivado -mode batch -source tools/synth_check_vision.tcl -nojournal`，看 `ERROR` 数量为 0。

### 顺带：`pin.xdc:49` 的警告

```
[Common 17-55] 'set_property' expects at least one object. [pin.xdc:49]
```

`set_property CLOCK_DEDICATED_ROUTE FALSE [get_nets cam_pclk_IBUF]` 抓的是**自动推导出来的网名**，
换版本/换综合设定就可能抓不到。这是**项目既有**的警告，与本次改动无关，不影响实现。

## 22. 多帧时间累积提灵敏度（P12，`temporal_acc.v`）

### 需求

把绿灯拉远，单帧掩码只剩几十个像素。某一帧因为反光、噪声、曝光抖动，面积掉到
`min_area_lo` 之下或形状判据不过，`blob_track` 就断链、目标消失一两帧 ——
后面的预测（P10）与弹道（P11）也跟着断。
P9 的宽松门坎只是「把要求放低」，补不了「这一帧根本没亮」。

### 为什么不是并集（OR）

迭 K 帧的 OR 会把**单帧噪点**也黏住（K 帧内任何噪点都留下），反而造出假目标。
这里用 **2 bit 饱和计数器**：

| 输入 | 动作 | 说明 |
|---|---|---|
| `mask=1` | `acc+1`（饱和到 3） | 命中 |
| `mask=0` | `acc−1`（饱和到 0） | 未命中 |
| 输出 | `acc ≥ thr`（预设 2） | |

- 单帧噪点：`acc` 只到 1，下一帧掉回 0 → **被拒绝**
- 真目标：连续两帧就黏住；中间丢一帧（3→2）仍在门坎上 → **黏住**
- 目标离开：2~3 帧不亮就自动回 0 → **不留残影**

### 电路

| 项 | 说明 |
|---|---|
| 存储 | `(* ram_style = "block" *) reg [1:0] acc_mem [0:WIDTH*HEIGHT-1]`（800×480 → 768Kb） |
| 地址 | `row_base = (y−1)×800`，用 `<<9 + <<8 + <<5` 代替乘法（800 = 512+256+32） |
| 单写埠 | 清空 FSM 与正常累加**共享**一个写埠：`we/waddr/wdata` 三根 wire 用 mux 选（多写埠会挡掉 RAM 推断，见 §7 与 §18） |
| 读出 | 同步读，1 拍 |
| 判据 | `acc_nx = mask_d1 ? sat(acc+1) : sat(acc−1)`（mask 也延 1 拍），再寄存一拍 |

### 时序对齐（关键）

输出延 **2 拍**（BRAM 同步读 1 拍 + 判据寄存 1 拍），所以 `x/y/de` 也**一起延 2 拍** ——
否则下游 `blob_track` 拿到的坐标与 mask 差 2 个像素，目标会整体横移。

### 直通（预设关闭）

```
byp = (~en) | clr | clr_run;
```

`en=0`、强制清零、自动清空期间走**零延迟直通**（`mask_o = mask_in`，`x_o = x`）。
所以 `TACC_EN = 1'b0`（预设）时，时序与行为与「不加这个模块」**逐位相同**，
可以放心先合入、等有需要再打开。

### 开机自动清空

复位后 FSM 对整个 RAM 写 0：384000 拍 ≈ **7.7ms @50MHz**，在一帧之内完成，
之后不再占用 BRAM 埠（所以不会偷走显示通路的带宽）。

### 资源

实测 **24 个 RAMB36**（768Kb，2bit×384000 → Vivado 用 16K×2 模式；占 7A35T 50 个的 **48%**），
是视觉管线里**唯一**用 BRAM 的地方（其余全部推给 LUTRAM，见 §7）。
加上原 39 例程的两条视频 FIFO 后仍能装下，但余量不宽裕：
若 BRAM 不够，把 `acc_mem` 位宽改成 1 bit（只存 `acc | mask`），成本减半（→ 12 个），
代价是单帧噪点也会被留一帧，那时得靠 `min_area_lo` 再兜一层。

### 寄存器

| 地址 | 位 | 作用 |
|---|---|---|
| `0x0C` | `[1:0]` | 累积门坎（预设 2） |
| `0x0C` | `[7]` | 写 1 → 立即清空累积器（场景切换 / 换场地时用） |

### 单元测试 / 复查抓到的四个问题（P12）

1. **写地址错一拍**：`waddr` 原本接 `adr_d`（延 2 拍），但 `we`（= `de_d`，延 1 拍）与
   `wdata`（= `acc_nx`，延 1 拍）同拍 → 等于「把当前像素的新值写到**上一个像素**的地址」。
   连续像素流下的症状是**累积掩码整体左移 1 像素、最右一列永远不累积**
   （关闭时完全看不出来）。修法：`waddr` 改用 `adr_w`（延 1 拍）与 `we`/`wdata` 对齐，`adr_d` 删掉。
2. **行首地址写死 ×800**：`row_base = (y−1)×800` 写死，`WIDTH` 只影响 `DEPTH`
   → 用小 `WIDTH` 做单元测试时地址全部越界（读出来是 X），测试根本没法写。
   改成 `(y−1) × WIDTH`（`WIDTH` 是常量，综合会化成移位相加，不会真的放乘法器）。
3. **取样时刻**：像素是在「**那个正沿**」被取样的（`de` 跨过一个正沿就够），
   输出（`mask_o` 与 `x_o/y_o/de_o`）在下一个正沿之后才有效
   → 测试要在**下一个正沿之后的半个周期**读，太早或太晚都会读到隔壁像素的值。
4. **软件强制清零（`0x0C` bit7）根本没接上**（复查时发现）：`clr` 原本只参与 `byp` 与写使能，
   **没有触发清空 FSM**（那个 FSM 只由复位启动）—— 按下去只停一拍累积，RAM 里旧值还在，
   正是典型的「文档写了、代码没接」。修法：`clr` 也触发清空 FSM（走完自动恢复累积）。
   两个测试台都补了检查：**清零前 `acc=2`（够门限），清零后同一像素再亮一帧必须不够（`acc=1`）**
   —— 这样才能区分「真的清掉了」和「只是旁路了一拍」。

> **`sim/tb_tacc.v`：秒级单元测试。** 主测试台一次要 8 分钟，改一次累积器就得等 8 分钟
> （本轮就是这样白跑了一轮）。这个只例化 `temporal_acc`（8×4）+ 稀疏像素流，
> `xvlog + xelab + xsim` 5 秒跑完，9 项自检（含「不亮那一帧真的写回内存了吗」）。
> 教训：**先写一个秒级单元测试再改 RTL**，比在主测试台里瞎猜快两个数量级。

### 验证（相位 14）

用 8×4 小实例（清空只要 32 拍）逐像素喂入，8 项自检：

| 检查 | 期望 | 验什么 |
|---|---|---|
| `tacc_hit1` | 0 | 只亮 1 帧 → 还不够 |
| `tacc_hit2` | 1 | 连中两帧 → 黏住 |
| `tacc_align_x` / `tacc_align_y` / `tacc_align_de` | 2 / 1 / 1 | `x/y/de` 与 `mask_o` 同拍（2 拍延迟） |
| `tacc_decay` | 0 | 灯走了 → 掉回门坎下 |
| `tacc_noise` / `tacc_noise_x` | 0 / 5 | 别处的单帧噪点被拒绝，且不影响坐标 |

### 与 `min_area_lo` 的关系

两者互补，不冲突：

- `min_area_lo`（P9）放宽的是「**这一帧的面积**要求」
- `temporal_acc`（P12）补的是「**这一帧缺失**」

远距离时一起用效果最好：有累积撑着，`min_area_lo` 可以再调低一档，
既不丢目标、也不至于把大面积噪点放进来。

## 23. P13：提前量物理化 + 板上合成靶标 + 状态页

### 23.1 P13c 距离自适应提前量（`aim_predict.v`）

**问题**：P10 的提前量是一个固定常数 `LEAD_Q4 = 64`（4.0 帧 ≈ 133ms @30fps）。
但真实飞行时间是 `t = 距离 / 弹速`：

| 距离 | 表观宽度 w | 飞行时间（20m/s） | 应提前 | 固定 4 帧的误差 |
|---|---|---|---|---|
| 5.05 m | 28 | 253 ms | 7.6 帧 | **少 3.6 帧** |
| 1.41 m | 100 | 71 ms | 2.1 帧 | 多 1.9 帧 |
| 0.71 m | 200 | 35 ms | 1.06 帧 | **多 2.9 帧（过冲 4 倍）** |

**做法**：距离已经由「表观宽度」隐含（`dist_cm = 14135/w`，见 §20），所以提前量同样只是 **1/w**：

```
t_flight = (14135/w) cm / 100 / 20 m/s
frames   = t_flight × 30 fps
lead_q4  = 16 × frames = 3392.4 / w
```

在 `aim_predict.v` 里加一张 `LEAD_MEM[256×8]`（与 `ballistic.v` 的两张表同源同写法：
`(* rom_style = "distributed" *)` + `initial`），查表只要一个 LUTRAM：

- `0x11 = 1`（预设）且 `w ∈ [12, 255]` → 用查表值
- `0x11 = 0`，或宽度不合理（太小/太大，距离不可信）→ 回退手动 `0x0A`

> 为什么要留手动回退：`3392.4` 这个系数假设弹速 20m/s、30fps。换弹簧/换弹速只要
> 改一个常数重跑 `tools/gen_lead_lut.py`；临时想试别的值就写 `0x0A` 并把 `0x11` 写 0。

### 23.2 P13a 板上合成靶标（`syn_target.v`）

**问题**：现场没有可复现的目标 —— 真人拿灯晃，速度不可控，预测/弹道这类依赖时序的功能没法验。

**做法**：一个 RTL 造的匀速往返绿圆，打开后直接顶替相机像素：

| 寄存器 | 作用 |
|---|---|
| `0x0F` | `[0]=1` 用合成靶标（`0` 回到相机，预设） |
| `0x0D` | 速度（**有符号 Q4** px/帧，`80` = 5.0 px/帧，负数反向；碰边自动往返） |
| `0x0E` | 半径（像素，预设 60 → 直径 120px，落在 §7.1 推荐取景范围） |

坐标约定：它用 `x_v / y_cnt` 组合画图，与 `data_v` **同一拍**，经 8 像素形态学偏移后
报出来正好是 `(408, 248)` —— 与仿真期望值完全一致，可以直接用 UART 上报的 `vx_q4`
和设定速度对表（速度精确已知，这是它最大的价值）。

踩过的三个坑（都是秒级单测 `sim/tb_p13.v` 抓出来的）：

1. `r2`（半径平方）原本只在 `vsync` 锁存 → 复位后第一帧 `r2 = 0`，**圆根本画不出来**。
   改成「`rad` 一变就重算」，复位后第一个周期就有效。
2. 改速度后要等一帧才生效（位置更新用了上一帧的 `vx_q4`）→ 改成「用新速度先试探、
   碰边就取反、再移动」，写 `0x0D` 立刻生效。
3. `{{(2*AW+2-24){1'b0}}, r2}` 这种写法在 `AW=10` 时是**负的重复次数**（xvlog 直接报错）
   → 改成 `r2[2*AW+1:0]`。

### 23.5 两个「时序」坑（OOC 预检从 +6.64 掉到 −2.89，再修回 +6.65）

**坑一：逐像素两个乘法。** 原来是 `dx² + dy² ≤ r²`，20ns 下串两个平方 + 加法 + 比较太长。
用圆方程化简：`dx² + dy² ≤ r²  ⟺  dx² ≤ (r² − dy²)`，而 `r² − dy²` 只跟行有关 →
用一个寄存器 `row_t` 逐拍算好（`y_cnt` 一行内不变，行间消隐足够它跟上），逐像素只剩「一个平方 + 一个比较」。
⚠️ `row_t` **必须有符号**：`dy² > r²` 时 `r² − dy²` 是负数，夹到 0 的话 `dx=0` 那一点会因为
`0 ≤ 0` 被凭空画出来（秒级单测的 `syn_bg_gray_v` 就是这个）。−2.888 → −1.293 ns。

**坑二：合成像素是组合出来的，和相机通路的「寄存过」的像素混在一个 mux 里。**
`cam_pix = syn_on ? syn_pix : data_v` —— 相机那路的第一级是寄存器 `data_v`，
合成那路却是从 `x_v` 直接组合出去，于是合成模式下整条下游比相机模式多一级组合。
实测最差路径 21.05ns：`x_v_reg → u_syn_target（乘法）→ median → color_seg → … → u_blob_track/emit_x0_reg/CE`。
修法：`pix` 打一拍（合成像素和 `data_v` 一样从寄存器出发），
打拍带来的「整图左移 1 像素」用比较时 `x+1` 抵消。−1.293 → **+6.654 ns**。

> 教训：**在「二选一」的 mux 里，两边的「深度」必须一致**。一边是寄存器、一边是组合逻辑，
> 下游就会按最差的那条算 —— 这是纯功能验收（仿真）看不出来的，只有综合/时序会抓。

### 23.3 P13d 板上状态页（`0x10`）

调参时不想接串口，所以让数码管/LED 兼作仪表：

| `0x10` | 数码管高位（3 位） | 数码管低位（2 位） | LED |
|---|---|---|---|
| 0 | 选中门坎值（原行为） | 目标宽度 ÷10 | 当前在调哪个门坎 |
| 1 | 距离（cm） | 下坠补偿 ÷10 | `pred_ok` / `moving` / `dist_ok` |
| 2 | 目标宽度（px） | 距离 ÷10 | 同上 |
| 3 | 速度（px/帧） | 目标宽度 ÷10 | 同上 |

实作上没有改 `seg_display.v`：三个门坎位都喂同一个值（模块会显示「当前选中」的那个，
三个一样就恒显示这个值），低位用 `bond_w`（模块内部做 `÷10`）。
⚠️ 注意 `seg_display.bond_w` 是 `[10:0]`，mux 必须**正好 11 位** —— 多一位少一位就是
§「端口位宽不匹配 = 高位悬空」那个坑。

### 23.4 P13b 加权形心：本轮没做（下一轮）

想用 `Σx·m / Σm` 代替外框中心，好处是光斑不规则（反光咬掉一块、被画面边缘裁掉）时更稳。
但这要动 `blob_track` 的**记录路径**（每条 run 的矩累加 → 匹配到团块 → 帧末做除法），
而它正好是之前把 50MHz setup 打爆、被三级流水抢救回来的那个模块 —— 风险最高、收益最小
（亚像素对「55mm 灯 ≈ 28px@5m」的瞄准精度其实已经够用），所以先留着。
真要做：每条 run 加 `sum_x/sum_y/cnt`（每像素一个加法器）、每团块记录加同样三个字段、
帧末用一个**串行除法器**（共享一个减法器，25 拍/次，垂直消隐有 47000 拍）算 `cx_q4/cy_q4`。

## 24. P14：斜置屏的框抖动 & 远距离灯的判定（现场反馈）

### 24.1 现象

* 屏幕**正放**时一切正常；
* 屏幕**斜置**（或侧向）时，绿色灯能识别出来，但**外框每帧变化很大** →
  黄十字（`pd_mov`）被反复激活、**乱闪**，非常不稳定；
* 灯**拉远**后只能高亮成「绿色」（`bl_ok`），判不出「是个灯」（不上报 `pd_ok`）。

### 24.2 因果链（为什么会抖）

```
屏斜置/角度变化 → 镜面反光 + AWB 随角度漂移 → color_seg 的边界在阈值附近来回咬
      → 形态学（9×9 close 后再腐蚀）后的外框每帧差十几像素
      → bw 抖 → 提前量(1.449w) / 距离(14135/w) / 下坠(4454.5/w) 全跟着抖
      → aim_predict 看到 cx/cy 帧间跳动（|v| ≥ 1px/帧）→ pd_mov = 1 → 黄十字乱闪
      → 上报给云台的 fx/fy 也在抖
```

要点：**根因是「尺寸测量」的抖动，不是「控制」的问题** —— 所以问题不在 PID/EKF（见 24.6），
而在「把每帧的原始外框先做一次抗野值，再算下游所有量」。

### 24.3 修法一：外框做 3 帧中值（`blob_track.v`）

对 `sl/sr/st/sb` 四条边各存 2 帧历史，输出取 **3 帧中值** `sl_f/sr_f/st_f/sb_f`，
再由它导出 `cx_f/cy_f/bw_f/aim_y_f`，最后写进 `bond_*/center_*/aim_*`（原来是直接写 4 条边的原始值）。

```verilog
function [AW:0] med3;                       // 三输入中值 = 排序后取中间
    ...
wire [AW:0] sl_f = have_hist ? med3({1'b0,sl_r}, hl1, hl2) : {1'b0, sl_r};
```

* **为什么是中值而不是 IIR/低通**：
  * 中值对「单帧野值」是**零拖尾**的（阶跃响应 1 帧、斜坡信号完全无偏），
    而一阶 IIR 对匀速运动目标会引入固定相位滞后 —— 正好会打坏相位 11 的提前量测试，
    也会让瞄移动目标时**指到目标后面**；
  * 中值不需要乘法（3 个数两次比较即可），50MHz 下是几级 LUT，零成本；
  * 只在「3 帧都有有效框」时才滤波（`have_hist`），
    **首个有效帧直接把历史装成同一值** → 静态场景与改动前**逐位一致**（相位 1 的检查原样通过）。
* 团块 `LOST`（`!sany_r`）时清 `have_hist`，避免拿上一段目标的历史去中值。
* 中值只能压「单帧野值」；真正连续的慢漂移仍要靠下游的 α-β 或 `min_area` 门限。

### 24.4 修法二：小团块免形状检查（远距离灯的关键）

宽松档（`min_area_lo`）原来要求 `shp_ok_r`（长宽比/填充率合格）。但远距离的灯只有几个像素，
**形状量本来就量化得很粗**（3×4 的团块，长宽比一抖动就出界），于是「面积够但形状不合格」→ 判不出灯。

```verilog
else if(r_used[mi] && (min_area_lo != 32'd0) &&
        (r_area[mi] >= min_area_lo) &&
        (shp_ok_r[mi] || (r_area[mi] <= 32'd32)))      // ← 小团块（≤32px）不看形状
```

`min_area_lo` 仍然独立控制宽松档的开关（`0` = 关闭，行为与旧版一致，逃生开关）。

### 24.5 修法三/四：运动灵敏度 & 运行时开关

* `aim_predict.v` 的 `MOVE_Q4` 由 `8'd16`（1 px/帧）提到 **`8'd32`（2 px/帧）**：
  斜置屏下即使中值后仍有 1px 级残抖，也不会把它当成「目标在动」而点亮黄十字。
* 新增 `0x12` 位0：可在运行中强制打开 α-β 跟踪器（`trk_on = TRK_EN | rf_flags2[0]`）。
  现场调参时，如果发现静态场景还在抖，可以直接打开它做二次平滑（跟 `TRK_EN` 的编译期开关不冲突）。

### 24.6 为什么不用 PID / EKF（回答提问）

| 方案 | 定位 | 能不能解决本问题 |
|---|---|---|
| PID | **控制器** —— 属于云台下位机（或上位机）的控制环，输入是误差、输出是电机量 | 不能。「测量本身在抖」时 PID 只会把抖动原样放大成电机抖动（D 项尤其怕测量噪声）；PID 该加在 `fx/fy` 之后的云台环里，本模块不做这件事 |
| EKF | 状态估计（浮点 + 矩阵求逆/协方差更新） | 不能。它假设「量测噪声是零均值小方差」；这里 `w` 的误差是**有偏的系统性抖动**（反光/阈值导致框大小变化），EKF 会把偏置当真值跟下去。RTL 里做浮点协方差也不现实（XC7A35T 的 DSP/时序都不划算） |
| **中值 + α-β + 迟滞** | 抗野值 + 平滑/测速 + 状态保持 | **对**。中值（本轮的 3 帧中值）先除野值；α-β（`track_ab.v`，已在流水线里）再做平滑和测速；`HIT_N/LOST_N`、`MOVE_Q4` 做迟滞。三件套都在定点/整数域，代价几个 LUT |

> 一句话：**先治「量」，再谈「控」**。本模块的职责是输出干净、可复现的 `fx/fy`；
> 抖动来自量测环节（分割→形态学→框），所以修在本模块，而不是引入一个更复杂的滤波器去「跟」抖动。
